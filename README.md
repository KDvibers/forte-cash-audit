# Forte Cash Audit

Сервис команды **KDvibers** для кейса ForteBank: загрузка кассового видео, локальный анализ и отчёт с событиями, таймкодами, нормативной ссылкой и настоящими кадрами исходного видео.

**Наш выбор для публичного доступа — Tailscale Funnel.** Он позволяет открыть сайт и API для жюри, сохранив завершение TLS на ноутбуке команды. Почему мы выбрали эту схему и отказались от прежнего Cloudflare Quick Tunnel, подробно объяснено [ниже](#funnel).

**Жюри не нужно скачивать модели, устанавливать Python или запускать сервер.** Откройте HTTPS-адрес из материалов сдачи: сайт, API и модели работают на ноутбуке команды. Для прямой проверки API команда отдельно передаёт ключ. Установка ниже предназначена только для самостоятельного воспроизведения проекта.

**Объём текущей версии:** один условный сигнал — банкноты остаются видимыми на рабочем столе после исчезновения человека из наблюдаемой рабочей зоны. Это основание для проверки человеком, а не автоматическое юридическое заключение. Другие действия с деньгами и второй тип про снятую одежду не включены в рабочий анализ.

## Проверить через сайт — без установки

1. Возьмите **актуальный адрес сайта** из формы сдачи или закрытого сообщения команды. Личный адрес и API-ключ намеренно не публикуются в репозитории.
2. Откройте адрес в браузере. Для публичного Funnel не нужно устанавливать Tailscale или входить в сеть команды. Во время проверки ноутбук команды должен быть включён, подключён к питанию и интернету; приложение, модели и публикация должны работать.
3. Дождитесь готовности сервера. На странице не должно быть пометки «Тестовый режим»: она означает синтетические ответы `mock`, которые не являются анализом загруженного видео.
4. Выберите файл **`.mov` размером до 100 MiB** — 104 857 600 байт. После выбора начинается загрузка и анализ. Сервер проверяет контейнер и возможность чтения; одного расширения `.mov` недостаточно.
5. Дождитесь результата. Передача файла, очередь и вычисления входят в обработку запроса. При медленной связи не отправляйте тот же файл повторно, пока не проверен статус первого задания.
6. В отчёте проверьте события, таймкоды, полное объяснение и ссылку на источник. Откройте доказательные кадры и сопоставьте их с исходным видео. Один результат может содержать несколько событий текущего типа.
7. После принятия задания можно обновить страницу: она восстанавливает сохранённое задание без повторной отправки. Для локального плеера после обновления может понадобиться снова выбрать тот же файл на устройстве — это не новая загрузка на сервер.

Браузер использует собственный протокол сессии. **Общий API-ключ в сайт вводить не требуется**; он предназначен для прямых запросов к API. Ошибка обработки не означает «нарушений нет».

Кадры можно увеличить, а по таймкоду — перейти к событию в исходном видео, если браузер поддерживает его кодек. Если видео не воспроизводится в браузере, события и JPEG-кадры остаются доступны. После обновления страницы запрашивается существующее задание, без повторного POST. Сохранённый готовый отчёт можно открыть и при недоступных моделях, пока работает приложение и не истёк срок хранения; истёкшая сессия и удалённый результат имеют отдельные сообщения.

Для контрольного замера включите секундомер **перед отправкой файла** и остановите после появления полного отчёта. Время на часах, длительность ролика и время вычисления модели не заменяют этот замер.

<a id="funnel"></a>
## Почему мы выбрали Tailscale Funnel

**Мы выбрали Tailscale Funnel как основной способ предоставить публичный интерфейс и API, сохранив расшифровку запросов на ноутбуке команды.** В кейсе одновременно требуются внешний адрес для проверки жюри, локальное выполнение моделей и запрет передачи тестовых видео третьим лицам. Мы сравнили способы публикации и выбрали маршрут, при котором внешнему ретранслятору не требуется доступ к содержимому видео.

### Где расшифровываются данные

> **TLS-соединение начинается в браузере или API-клиенте и завершается в Tailscale на ноутбуке Данияра. Ретранслятор Funnel передаёт зашифрованный поток, не расшифровывая видео, API-ключ и кадры результата.** Это устройство маршрута описано в [официальной документации Tailscale](https://tailscale.com/docs/features/tailscale-funnel#how-funnel-works).

После расшифровки запрос поступает нашему backend по HTTP через `127.0.0.1:8020` **внутри того же ноутбука**. Открытое содержимое этого локального участка не пересылается между ноутбуками или через интернет. Ответ возвращается клиенту через защищённое соединение.

В прежней стандартной схеме **Cloudflare Quick Tunnel** внешнее TLS-соединение завершалось на стороне Cloudflare. У Cloudflare клиентское соединение и соединение к исходному серверу имеют отдельные границы TLS — см. [официальное описание edge и origin](https://developers.cloudflare.com/ssl/concepts/). Поэтому причиной перехода стало **место расшифровки содержимого**. Прежний маршрут тоже использовал шифрование при передаче; одного наличия HTTPS недостаточно, чтобы определить, кто может прочитать содержимое.

### Публикация и анализ выполняют разные задачи

Funnel предоставляет сетевой доступ. **Настоящий анализ выполняют локальные модели на ноутбуке Данияра**; Funnel не вызывает облачный AI. На этом же ноутбуке работают интерфейс и backend. Ноутбук Касымбека использовался для разработки приложения и проверки публикации; в текущем рабочем маршруте он не является промежуточным сервером для банковских видео. Жюри открывает обычную HTTPS-ссылку без установки Tailscale или VPN.

Подготовку маршрута Касымбек проверял на синтетическом MOV размером около 29 МБ: полный путь в `mock` занял 107,49 с, включая 104,91 с загрузки. Это историческая проверка передачи, а не качества AI. Затем на ноутбуке Данияра проверили объединённый `real`: настоящие видео, API, отчёт и кадры, в том числе загрузку с внешнего телефона. Условия, успешные замеры и неудачи приведены в [подтверждённых проверках](#verification).

### Границы выбранной защиты

Мы не утверждаем, что сторонняя инфраструктура отсутствует: через неё проходит зашифрованный поток. Защита содержимого при передаче не означает сокрытие всех сетевых метаданных, шифрование файлов на диске или отсутствие журналов у провайдера. Отдельного разъяснения организаторов о допустимости зашифрованного транзита у команды нет. Поэтому мы раскрываем архитектуру и основание выбора, не заявляя об отдельном одобрении этой схемы организаторами.

Порядок настройки и первоначальные замеры — в [руководстве Funnel](docs/FUNNEL_ACCESS.md), последующие проверки настоящего сервиса — в [статусе интеграции](docs/FUNNEL_INTEGRATION_STATUS.md). [Прежний вариант Cloudflare](docs/PUBLIC_ACCESS.md) сохранён как история технического решения; основной запуск его не использует.

## Наша особенность: проверяемое обоснование каждого сигнала

Мы строим результат так, чтобы проверяющий мог пройти всю цепочку: **наблюдаемое условие → подтверждение во времени → конкретные кадры → нормативный источник и условия его применения**. В описании события различаются первое совпадение условий, последующее подтверждение и границы наблюдаемого изменения. Если подтверждённые фрагменты разделены промежутком, отчёт сообщает об этом.

Проверяющий видит настоящие JPEG из загруженного видео, может увеличить их, перейти к таймкоду и открыть источник. Анализатор сверяет SHA-256 исходного файла до и после обработки и проверяет соответствие доказательных JPEG сохранённым кадрам. Эти проверки помогают обнаружить изменение файлов; сами по себе они не доказывают правильность ответа модели. Контрольные суммы сохраняются в локальных материалах анализа, а публичный API возвращает поля согласованного контракта.

| Связь с кейсом | Как это реализовано | Что может проверить жюри |
| --- | --- | --- |
| **Качество локализации — 15 баллов** | Время исходного видео, отдельный момент подтверждения и 1–3 кадра события | Совпадают ли таймкод и кадры с наблюдаемым эпизодом |
| **Обоснованность правил — 15 баллов** | Источник из локального каталога, конкретный пункт и объяснение условий применимости | Поддерживает ли источник именно этот вывод, нет ли неподтверждённых утверждений |
| **Локальность и архитектура** | Локальные модели и публичный доступ через Funnel с завершением TLS на ноутбуке | Где выполняется анализ и где расшифровывается содержимое запроса |

Сейчас эта цепочка работает для **одного включённого условного денежного сигнала**. Точность таймкода, применимость нормы и качество на новых ракурсах требуют отдельной оценки; наличие такой цепочки не гарантирует баллы. Технически незавершённый анализ не превращается в ответ «нарушений нет».

<a id="api"></a>
## Проверить через API

Используйте базовый HTTPS-адрес из материалов сдачи и переданный приватно ключ. `https://YOUR-SERVICE.example` ниже — обозначение адреса, не работающий сервер.

| Маршрут | Назначение | Авторизация |
| --- | --- | --- |
| `GET /health` | Режим и готовность | Без ключа |
| `POST /api/v1/analyze` | Загрузить MOV, получить `job_id` | Заголовок `X-API-Key` |
| `GET /api/v1/jobs/{job_id}` | Получить статус или результат | Заголовок `X-API-Key` |

У `/health` одновременно нужны `status="ok"`, `mode="real"`, `analyzer_ready=true`. Один HTTP 200 не подтверждает готовность настоящего анализатора.

### Отправка и опрос

В Postman, Insomnia или своём HTTP-клиенте:

1. Создайте `POST https://YOUR-SERVICE.example/api/v1/analyze`.
2. Добавьте заголовок `X-API-Key` со значением от команды. Храните его в приватной переменной клиента, не в публичной коллекции, исходном коде или журнале.
3. Выберите **multipart/form-data**. Имя поля — **`file`**, тип — File, значение — MOV. Не используйте поле `video`, JSON или base64 вместо multipart-файла. Границу multipart пусть формирует клиент.
4. Сохраните `job_id` из ответа. Сервер возвращает идентификатор, не ожидая окончания анализа.
5. Выполняйте `GET https://YOUR-SERVICE.example/api/v1/jobs/{job_id}` с тем же заголовком примерно раз в две секунды. Прекратите опрос после `done` или `failed`. Сетевой сбой не является основанием автоматически повторять POST.

Промежуточный ответ, включая ожидание очереди:

```json
{"job_id":"example-job","status":"processing"}
```

Успешный ответ без обнаруженного поддерживаемого сигнала:

```json
{
  "job_id": "example-job",
  "status": "done",
  "verdict": "no_violation",
  "violations": []
}
```

При найденных событиях `verdict` равен `violation`, а `violations` содержит один или несколько элементов:

| Поле события | Содержание |
| --- | --- |
| `type` | Название типа события |
| `timecode_sec` | Время первого совпадения условий в секундах исходного видео, включая дробную часть |
| `description` | Наблюдаемый факт, условия и ограничения вывода, нормативная ссылка |
| `evidence_frames` | От 1 до 3 доказательных кадров этого события |

У кадра есть `timestamp_sec` и `image_base64`. Последнее — **JPEG в base64 без префикса** `data:image/jpeg;base64,`. Для HTML клиент добавляет префикс сам. В рабочем режиме это реальные кадры входного файла. Кадры не следует печатать в общедоступные журналы.

Ошибка анализа:

```json
{"job_id":"example-job","status":"failed"}
```

У `failed` нет отрицательного вердикта. HTTP 200 при опросе также не означает `done`: проверяйте `status`. Полный контракт — [docs/API_CONTRACT.md](docs/API_CONTRACT.md).

### Необязательный клиент для измеряемой API-проверки

Готовый клиент опрашивает задание и проверяет JSON, JPEG и полный срок. Он **не запускает модели и не требует GPU**. Для использования достаточно кода репозитория и небольшой клиентской среды; можно вместо него использовать свой клиент по контракту выше.

Из корня скачанного репозитория, с установленным Python 3.12 x64:

```powershell
py -3.12 -m venv .venv-client
if ($LASTEXITCODE -ne 0) { throw 'Не удалось создать клиентскую среду' }
.\.venv-client\Scripts\python.exe -m pip install Pillow==11.3.0 imageio-ffmpeg==0.6.0
if ($LASTEXITCODE -ne 0) { throw 'Не установлены зависимости клиента' }
```

Сохраните переданный ключ в отдельный текстовый файл **вне репозитория**. Укажите адрес и пути, не вставляя значение ключа в командную строку:

```powershell
$ServiceUrl = Read-Host 'HTTPS-адрес из материалов сдачи'
$JuryKeyFile = Read-Host 'Полный путь к приватному текстовому файлу с ключом'
$VideoFile = Read-Host 'Полный путь к разрешённому MOV'
.\.venv-client\Scripts\python.exe -m backend.check_real `
  --base-url $ServiceUrl --key-file $JuryKeyFile --video $VideoFile --channel api
if ($LASTEXITCODE -ne 0) { throw 'Проверка не завершилась успешно; прочитайте отчёт' }
```

Клиент проверяет режим `real`, включает передачу, очередь, получение результата и валидацию JPEG в лимит 300 секунд; повторного POST не делает. Краткий отчёт сохраняется в `backend/.local/check-real/`, без ключа и base64 кадров. Структурная проверка не доказывает правильность распознавания: содержание нужно сопоставить с видео. Параметр `--require-events` для произвольного ролика не нужен.

<a id="result"></a>
## Что означает результат

Правило `cash_visible_after_person_disappears` ищет последовательность:

1. На двух выбранных кадрах подтверждено присутствие человека в рабочей зоне.
2. Затем два последовательных выбранных кадра показывают банкноты на столе и отсутствие человека в наблюдаемой зоне.
3. Программа связывает подтверждения в событие и прикладывает исходные кадры. Фрагменты одного эпизода объединяются; возвращение человека позволяет отделить следующий эпизод.

Банкноты в руках или счётной машине не равнозначны банкнотам на столе. Модель учитывает стеклянную перегородку и проём, но не устанавливает личность, должность или полномочия человека.

Связанный источник — пункт 20, абзац 2 Правил НБРК № 231; ссылка и условия разобраны в [правилах проекта](docs/RULES.md). Применимость зависит, в частности, от того, являются ли деньги ранее принятыми наличными. По изображению нельзя надёжно установить принадлежность денег, завершение обслуживания или все условия хранения. Поэтому `violation` означает признаки **возможного** нарушения для последующей проверки, а не установленное нарушение закона.

`no_violation` означает, что текущая проверка завершилась без обнаружения этого сигнала на выбранных кадрах. Это **не заключение об отсутствии всех нарушений** в видео. Если данных недостаточно для публикации проверенного результата либо проход технически не завершён, сервер возвращает `failed`, а не подставляет отрицательный результат.

Таймкод относится к исходному видео. В проверенном ролике 26 событие начинается с модельного совпадения **17,8 с**, подтверждаемого следующим кадром примерно **19,77 с**. Это не точная физическая секунда ухода человека. Расхождение с исходной отметкой организаторов 9 с не разрешено.

### Что пока не поддерживается

- Надёжное различение загрузки банкнот в счётчик и извлечения, перенос денег в шкаф, поиск всех коротких действий.
- Проверка всех требований кассовой дисциплины или содержимого закрытых зон.
- Подтверждённое обобщение на другой ракурс, стол и оборудование: рабочий профиль проверялся на знакомом ракурсе и использует признаки деревянного стола.
- Второе правило про снятую верхнюю одежду: код подготовлен, но оно выключено. Каскад 4B → 8B и отдельный исполнитель второго ноутбука также не подключены к `analyze_video`.

Рабочий просмотр выбирает кадры примерно раз в две секунды, не более 80 по ролику. В длинной записи промежуток увеличивается; короткое действие между кадрами может быть пропущено. Аудио не используется, люди по лицу не идентифицируются.

По [исходному плану из семи этапов](docs/PROJECT_PLAN.md) этапы 1–2 выполнены, этапы 3–5 частичны. Основной путь этапа 6 проверен для текущего профиля; этап 7 — итоговые проверки. Один работающий тип не закрывает полный объём кейса.

## Устройство анализа и защита передачи

```text
Браузер / API-клиент жюри
        │ HTTPS
        ▼
Funnel: ретрансляция зашифрованного потока
        │ TLS завершается на ноутбуке команды
        ▼
FastAPI на 127.0.0.1:8020
        │ загрузка → очередь одного исполнителя → анализатор
        ├─ Qwen3-VL-2B: 127.0.0.1:8080
        └─ Qwen3-VL-4B: 127.0.0.1:8081
        │ наблюдения → временное правило → исходные JPEG
        ▼
JSON API / отчёт на сайте
```

Две готовые модели Qwen3-VL работают через llama.cpp. 4B выбирает рабочую область и уточняет положение человека/денег, 2B проверяет банкноты в выбранной области. Веса загружены заранее и переиспользуются; одновременно выполняется одно задание анализа. Исследовательские детекторы и 8B для рабочего запуска не нужны.

Видео, кадры и их описания не отправляются во внешние AI-сервисы. Нормативная ссылка берётся из локального каталога. Сохраняется проверяемая цепочка «наблюдения → временные условия → время исходного кадра → JPEG → источник»; SHA-256 помогает проверить неизменность входа и доказательств.

Граница TLS, причина выбора Funnel и ограничения защиты подробно описаны в разделе [«Почему мы выбрали Tailscale Funnel»](#funnel). Модельные порты 8080 и 8081 наружу не публикуются.

GitHub хранит исходный код. Само наличие репозитория не запускает анализ и не публикует приложение: для проверки жюри используется работающий сервис на ноутбуке команды.

## Запустить подготовленный ноутбук команды

Этот раздел нужен оператору, а не проверяющему, открывающему готовый сайт. Модели, runtime, `.venv-app` и Tailscale предполагаются уже установленными.

Сначала штатно остановите прежнее приложение/Funnel, если планируете перезапуск. Если сервис уже работает и принимает задания, второй экземпляр не нужен. Подключите питание, сохраните интернет и не переводите ноутбук в сон во время проверки.

Откройте PowerShell **в корне проекта**, где находятся `README.md`, `analyzer/`, `backend/`, `scripts/`. Выполните блок целиком: проверки кода выхода останавливают его при ошибке.

```powershell
$ErrorActionPreference = 'Stop'
powershell -ExecutionPolicy Bypass -File .\scripts\real.ps1 -Port 8020 -StartModels -CheckOnly
if ($LASTEXITCODE -ne 0) { throw 'Модели или real-профиль не готовы. Далее не продолжать.' }

powershell -ExecutionPolicy Bypass -File .\scripts\funnel-real.ps1 -CheckOnly
if ($LASTEXITCODE -ne 0) { throw 'Проверка Funnel не пройдена. Публикация не запущена.' }

powershell -ExecutionPolicy Bypass -File .\scripts\funnel-real.ps1
if ($LASTEXITCODE -ne 0) { throw 'Запуск Funnel завершился с ошибкой. Проверьте журнал.' }
```

Первый вызов запускает только отсутствующие серверы моделей и проверяет обе роли, без запуска приложения. Занятые порты не освобождаются. Второй проверяет готовность публикации. Третий запускает **real** сайт/API и Funnel. Терминал нужно оставить открытым; актуальный HTTPS-адрес берётся из его вывода.

Для жюри используйте именно **`scripts/funnel-real.ps1`**. Общий `scripts/public-funnel.ps1` по умолчанию выбирает `mock`; его прямой запуск без режима не является настоящим анализом.

В другом PowerShell проверьте полученный адрес:

```powershell
$ServiceUrl = (Read-Host 'HTTPS-адрес из вывода Funnel').TrimEnd('/')
$Health = Invoke-RestMethod -Uri ($ServiceUrl + '/health') -TimeoutSec 10
if ($Health.status -ne 'ok' -or $Health.mode -ne 'real' -or $Health.analyzer_ready -ne $true) {
    throw 'Сервис ещё не готов к настоящему анализу'
}
$Health | Select-Object status, mode, analyzer_ready
```

Проверка с этого ноутбука может выбрать частный маршрут Tailscale. Для внешней проверки откройте обычный адрес на телефоне через мобильную сеть без Wi-Fi/Tailscale/VPN и загрузите разрешённый MOV.

### Разные режимы — разные данные и ключи

| Назначение | Команда | Адрес приложения | Данные и ключ |
| --- | --- | --- | --- |
| Публикация для жюри | `scripts/funnel-real.ps1` | `127.0.0.1:8020` за HTTPS Funnel | `backend/.local/funnel-real/`, внутри `api-key.txt` |
| Только локальная проверка | `scripts/real.ps1` | `http://127.0.0.1:8000` | `backend/.local/real/`, свой `api-key.txt` |
| Синтетическая демонстрация UI | `scripts/demo.ps1` | `http://127.0.0.1:8000` | `backend/.local/demo/`; явно `mock` |

Ключ локального real-запуска не подходит для другого хранилища Funnel. Значение ключа скрипты не печатают; оно не входит в frontend. Оператор передаёт его проверяющему приватно.

Для локального режима вместо публикации:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\real.ps1 -StartModels
if ($LASTEXITCODE -ne 0) { throw 'Локальный real-запуск завершился с ошибкой' }
```

Откройте `http://127.0.0.1:8000`. Не запускайте одновременно локальное приложение и Funnel как два анализатора одной GPU. Модели на 8080/8081 слушают только localhost.

## Самостоятельное воспроизведение на Windows

**Необязательно для жюри.** На новом компьютере среда создаётся заново: копирование готовой `.venv-app` не заменяет установку.

### 1. Подготовить систему и получить код

Нужны Windows x64, Git, **CPython 3.12 x64**, интернет для скачивания и совместимый NVIDIA-драйвер. Проверенный компьютер: RTX 5070 Laptop с 8 ГБ видеопамяти, Ryzen 7 7745HX, 32 ГБ RAM. Это описание проверенной машины, а не установленные минимальные требования для любых GPU.

Закреплённый runtime — llama.cpp `b11669`, Windows x64, **CUDA 13.4**. Нужен драйвер, совместимый с этой сборкой. [NVIDIA указывает для семейства CUDA 13.x базовую ветку от 580](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html), с дополнительными ограничениями совместимости. На драйвере 566.07 получена ошибка `cudaErrorInsufficientDriver`; CPU-переход не принят как рабочий профиль. Чистая установка на произвольной другой конфигурации не проверена.

Python: [официальные выпуски для Windows](https://www.python.org/downloads/windows/). Если `py -3.12` не находит установку, используйте полный путь к своему Python 3.12 x64. Node.js 22+ нужен только для frontend-тестов: сайт — статика, отдельной npm-сборки нет. PyTorch, 8B и исследовательский детектор для сервиса не нужны.

Получите доступ к [репозиторию команды](https://github.com/KDvibers/forte-cash-audit). Если он закрыт, доступ выдаёт команда. Скачайте код:

```powershell
git clone https://github.com/KDvibers/forte-cash-audit.git
if ($LASTEXITCODE -ne 0) { throw 'Репозиторий не скачан; проверьте доступ' }
Set-Location -LiteralPath .\forte-cash-audit
```

Используйте **опубликованный коммит из материалов сдачи**. Если он отличается от скачанной ветки, переключитесь на него в новой копии. До публикации этой версии Данияром инструкция не означает, что все локальные изменения уже находятся в GitHub. В выбранной версии должны существовать `scripts/real.ps1` и `scripts/funnel-real.ps1`.

Для выбора конкретного опубликованного коммита в новой копии:

```powershell

git checkout --detach $SubmissionCommit
if ($LASTEXITCODE -ne 0) { throw 'Коммит не найден; уточните опубликованную версию у команды' }

```

Видео, доказательные кадры, секреты, окружения, веса и результаты исследований в Git не включаются. Четыре рабочих GGUF занимают около **5,26 ГБ**; дополнительно нужны место для runtime, кэшей, Python, загрузок и отчётов. Это не общий размер установки.

<a id="operations"></a>
## Остановка, восстановление и ошибки

**Остановка:** Ctrl+C в терминале `funnel-real.ps1`, затем дождаться завершения. Закрываются собственные приложение и публикация; модели остаются загруженными. Для обычной остановки не нужен общий сброс Tailscale.

**Хранение:** данные Funnel — `backend/.local/funnel-real/`. Завершённые задания и их загрузки хранятся по текущей настройке 24 часа после завершения; перезапуск срок не продлевает. Штатная очистка заданий не удаляет API-ключ. Незавершённые при перезапуске задания получают `failed` и автоматически заново не запускаются.

**Бюджет:** сервер выделяет 285 секунд от входа запроса, анализатору — не более 260 секунд и только оставшееся время с запасом на ответ. Принимаются максимум два незавершённых запроса с учётом загрузок; GPU обрабатывает один, второй ждёт в пределах своего срока. Третий получает 429. Полный клиентский лимит 300 секунд включает передачу и очередь; серверный лимит не гарантирует его на медленной сети.

| Симптом | Действие |
| --- | --- |
| `mock` / «Тестовый режим» | Использовать экземпляр через `funnel-real.ps1`. Синтетический ответ не считать анализом. |
| Ошибка ключа API | Проверить заголовок и ключ нужного экземпляра. Ключи локального сервиса и Funnel различаются. |
| 429 | Дождаться свободной очереди; не создавать повторные загрузки. |
| 422 / файл отклонён | Проверить MOV, размер и читаемость. Отклонённый файл не получил заключения. |
| `failed` из-за недостаточных визуальных данных | Прочитать сообщение. Это не отсутствие нарушений; при готовом `/health` перезапуск моделей не требуется. |
| 503 после технического сбоя/таймаута | Остановить новые загрузки, проверить модели и отсутствие продолжающейся работы перед перезапуском. |
| Страница или имя недоступны | Проверить питание, сеть, терминал и `tailscale funnel status`. Не выполнять общий `reset`, `down` или отключение TLS. |

После таймаута блокировка предотвращает новое задание поверх вызова модели, который мог ещё выполняться. Проверка обеих моделей и каждого слота:

```powershell
foreach ($ModelPort in @(8080, 8081)) {
    $ModelHealth = Invoke-RestMethod -Uri "http://127.0.0.1:$ModelPort/health" -TimeoutSec 5
    [pscustomobject]@{ port = $ModelPort; status = $ModelHealth.status }
    foreach ($Slot in (Invoke-RestMethod -Uri "http://127.0.0.1:$ModelPort/slots" -TimeoutSec 5)) {
        [pscustomobject]@{ port = $ModelPort; id = $Slot.id; is_processing = $Slot.is_processing }
    }
}
```

Нужны оба `status=ok` и все `is_processing=false`. Если работа продолжается, дождитесь завершения. Если модель зависла или состояние неизвестно, сначала разберите её журнал и собственный процесс; не запускайте второй поверх занятого порта. Журналы: `runs/model-server/`, `runs/model-server-8081/`.

Только после подтверждения простоя остановите приложение штатно и повторите запуск. `-StartModels` запускает отсутствующие модели, но не заменяет зависшие процессы. После восстановления проверьте `real`, готовность и один известный сценарий. Полный порядок — [REAL_RUNBOOK.md](docs/REAL_RUNBOOK.md).

## Команда и вклад участников

Проект подготовила команда **KDvibers: Данияр и Касымбек**.

| Участник | Зона ответственности и выполненная работа |
| --- | --- |
| **Данияр** | Анализатор в `analyzer/`: подготовка локальных моделей и GPU, извлечение кадров и временных отметок, проверка распознавания на видео, временные правила, нормативные связи, настоящие кадры-доказательства и оценка ошибок. Подготовка рабочего ноутбука для настоящего анализа. |
| **Касымбек** | Весь интерфейс в `frontend/`, включая экран результатов, и сервер приложения в `backend/`: загрузка MOV, задания, статусы, авторизация API, отображение событий и кадров, восстановление отчёта. Подготовка запуска через Tailscale Funnel, диагностики, остановки и инструкций переноса. |
| **Совместная работа** | Согласование API-контракта, объединение анализатора с приложением, развёртывание на ноутбуке Данияра с RTX 5070, проверки полного пути загрузки и выдачи результата, проверка внешнего доступа. |

Разделение сохраняется: Данияр отвечает за анализатор, Касымбек — за весь интерфейс, экран результатов и backend приложения. Тесты и экспериментальный запуск 8B на втором ноутбуке не означают, что он включён в рабочий анализ.

Рабочие ветки — `analyzer` и `web-api`. Перед объединением просматриваем изменения; итоговые push и PR выполняет Данияр. Сохраняем настоящее авторство участников и не передаём учётные данные. Подробное распределение — [задача Касымбеку](docs/TEAMMATE_TASK.md).

## Структура проекта и документация

| Путь | Назначение |
| --- | --- |
| `frontend/` | Статический интерфейс: загрузка, ожидание, отчёт, кадры |
| `backend/` | FastAPI, загрузки, задания, авторизация, очередь, диагностические клиенты |
| `analyzer/` | Локальные наблюдения, временные правила, источники, доказательства |
| `analyzer/service.py` | Вход `analyze_video(video_path, *, budget_sec=260.0)` для сервера |
| `scripts/` | Команды локального и публичного запуска |
| `docs/` | Контракт, правила, ограничения, измерения и инструкции |
| `models/`, `.cache/`, `.venv-app/`, `runs/`, `backend/.local/` | Локальные файлы вне Git; не часть исходного кода |

Анализатор возвращает смысловой результат, backend добавляет идентификатор задания и статус, интерфейс отображает ответ. Для разработки сохранён явно обозначенный `mock` с синтетическими данными; рабочий режим `real` не подменяется им при ошибке.

- [Контракт API](docs/API_CONTRACT.md) — поля, статусы и время.
- [Правила и ограничения](docs/RULES.md) — условия и нормативная привязка.
- [Запуск и восстановление](docs/REAL_RUNBOOK.md) — инструкция оператору.
- [Настройка Funnel](docs/FUNNEL_ACCESS.md) — устройство маршрута и исторический протокол подготовки.
- [Демонстрация без моделей](docs/DEMO_GUIDE.md) — отдельный локальный `mock`, синтетический пример и проверка приложения; это не анализ банковского видео.
- [Интерфейс](frontend/README.md) и [сервер приложения](backend/README.md) — устройство, проверка и восстановление.
- [Протокол интерфейса](docs/submission/UI_REHEARSAL.md) — сценарии и результаты проверок.
- [Состояние интеграции](docs/FUNNEL_INTEGRATION_STATUS.md) — прогоны, маршруты и неудачи.

- [Компоненты и лицензии](docs/COMPONENTS.md) — зависимости, источники и SHA-256.
- [Анализатор](analyzer/README.md) — технические подробности исследований.
- [Материалы сдачи](docs/submission/README.md) — состав комплекта; личный адрес, ключ и окончательная версия передаются отдельно.

Веса и внешние бинарные файлы не распространяются этим репозиторием. Лицензии компонентов различаются: Apache-2.0 моделей или MIT llama.cpp не являются лицензией всех DLL, FFmpeg, Tailscale или всего проекта. Перечень компонентов не заменяет полный юридический аудит зависимостей.

Исходные видео, разметка, извлечённые кадры, локальные материалы просмотра, веса моделей, загрузки пользователей и секреты остаются вне Git. Локальные каталоги `review/`, `runs/` и `backend/.local/` не входят в публикуемый исходный код.
