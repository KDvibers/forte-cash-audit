# Первый локальный запуск модели

Этот каталог содержит инструменты проверки понимания видео. Они пока не являются готовым анализатором нарушений и не реализуют публичный API. Точка входа `analyze_video` для интеграции будет добавлена после проверки модели и правил.

## Результат первого запуска — 17 октября 2026

Локальный запуск на RTX 5070 Laptop с 8 ГБ видеопамяти подтверждён. Проверены один кадр, два кадра, четыре коротких видео и одно видео длительностью около 143 секунд. Одинаковый первоначальный запрос применён без передачи разметки модели.

- Один кадр вместе с извлечением из видео: 1,80 с.
- Четыре коротких видео, по 12 кадров: 6,89–7,36 с на видео.
- Длинное видео, также 12 кадров: 12,62 с, из них 6,30 с — извлечение кадров.
- Наибольшее наблюдаемое потребление всего GPU в основной серии: 3153 MiB, примерно 3,08 GiB.

Это измерения диагностического запуска, а не готового анализа нарушений: очередь, загрузка исходного файла и первоначальная загрузка модели в эти времена не входят. Редкая выборка из 12 кадров не обеспечивает полноту анализа.

Качество первоначального общего описания оказалось недостаточным: модель теряет изменения между кадрами и путает состояния объектов. Два из пяти ответов с 12 кадрами оборвались на лимите 768 токенов. Технический статус `completed` означает завершённый JSON-ответ, а не правильность наблюдений. В дополнительной проверке простой вопрос по двум изображениям дал правильное различение присутствия человека, но подробный структурированный запрос и отдельные запросы по кадрам оставались ненадёжными. Ограничение vision batch до одного изображения не исправило исходный результат.

Вывод этапа 1: оборудование и локальная цепочка работают; пригодность текущего запроса и модели для правил не подтверждена. Следующий этап — сравнить короткие наблюдения, контекст и крупные области объектов, проверять формат ответов и визуальную точность. Увеличение лимита ответа само по себе не решает ошибочное распознавание. Локальные подробные отчёты и кадры хранятся в исключённой из Git папке `runs/`.

## Что мы запускаем

- Qwen3-VL-2B-Instruct: языковая часть Q4_K_M и визуальный компонент F16.
- Официальный llama.cpp b11669, Windows x64, CUDA 13.4.
- Python 3.12 с PyAV и Pillow для извлечения настоящих кадров и временных отметок.

Точные версии, источники и SHA-256 весов и runtime зафиксированы в `runtime-lock.json`. Первичная установка использует интернет. Во время анализа картинки передаются только на локальный адрес `127.0.0.1`; внешний AI-сервис не используется.

## Установка

Команды ниже выполняются из корня проекта в PowerShell. На этой рабочей машине окружение `.venv` уже создано. На новом компьютере сначала нужен Python 3.12 и `python -m venv .venv`.

Текущее окружение используется для диагностических запусков анализатора. Не устанавливайте поверх него требования backend до согласования зависимостей: анализатор закрепляет Pillow 11.3.0, сервер — Pillow 13.0.0. Объединение или разделение окружений для рабочего приложения относится к этапу интеграции.

```powershell
.\.venv\Scripts\python.exe -m pip install -r analyzer\requirements.txt
.\.venv\Scripts\python.exe -m pip install -r analyzer\requirements-setup.txt
.\.venv\Scripts\python.exe analyzer\bootstrap_windows.py
```

При медленной загрузке Hugging Face можно использовать официальный репозиторий Qwen на ModelScope с проверкой тех же SHA-256:

```powershell
.\.venv\Scripts\python.exe analyzer\bootstrap_windows.py --model-source modelscope
```

Веса лежат в `models/`, программа запуска — в `.cache/`. Эти папки исключены из Git. Загрузчик не обновляет драйвер, не меняет глобальный Python и не отправляет данные датасета в интернет.

## Запуск модели

```powershell
.\analyzer\start_model.ps1
```

Терминал показывает журнал работы. Для остановки этого запуска используется Ctrl+C. Вариант `-Background` запускает отдельный скрытый процесс; его PID и журналы сохраняются в `runs/model-server/`. Сообщение о создании процесса ещё не означает готовность модели: нужно дождаться успешного ответа `http://127.0.0.1:8080/health` и строки о загрузке модели в журнале.

Стартовые настройки: один исполнитель, контекст 8192 токена, максимум 512 визуальных токенов на изображение. Это параметры первого эксперимента, не доказанный оптимум. Порт 8080 принадлежит внутреннему серверу модели, а не API жюри.

## Проверка одного видео

В другом терминале:

```powershell
.\.venv\Scripts\python.exe -m analyzer.smoke "C:\путь\к\video.mov" --frames 12 --out runs\my-video-check
```

Программа равномерно выбирает до 12 настоящих кадров по всему видео, включая начало и конец. Она сохраняет кадры, их фактические времена, ответ модели, длительность обработки и наблюдения за памятью видеокарты. Путь и имя файла не включаются в запрос модели; разметка организаторов не читается.

Для первичной проверки одного изображения используется дополнительный параметр `--single-image`; тогда из выбранной последовательности отправляется только средний кадр. Для проверки связи двух кадров можно указать `--frames 2`.

## Как читать результаты

JSON-файлы и изображения находятся в указанной папке `runs/`, исключённой из Git. `events` — описания видимых действий, `final_state` — состояние последнего кадра. Это наблюдения модели, которые нужно сопоставить с изображениями вручную; они не равны доказанным нарушениям.

`total_seconds` включает извлечение кадров, локальный запрос модели и сохранение результата. `request_seconds` показывает время запроса к модели. `peak_observed_device_memory_mib` — наибольшее наблюдаемое потребление всей видеокарты при периодическом опросе; это не точный аппаратный максимум и не память только данного процесса. Начальная загрузка модели и ожидание очереди вне этого отдельного запуска в показатель не входят.

Одинаковый промпт применяется к положительным и отрицательным роликам. Его контрольная сумма сохраняется в отчёте. Все уже просмотренные ролики используются здесь для разработки, а не как независимый скрытый тест.

12 кадров не гарантируют обнаружение быстрого действия, особенно в длинном видео. Первый эксперимент проверяет работоспособность и базовое понимание сцены. Точная локализация, дополнительные кадры подозрительных интервалов, проверка нормативных условий и окончательный API-вердикт — следующие этапы.
