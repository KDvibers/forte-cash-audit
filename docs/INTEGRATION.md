# Этап 6: настоящий анализ через приложение

Сайт и сервер Касымбека вызывают анализатор Данияра на RTX 5070. Выбор MOV запускает обработку автоматически. Публичный API жюри и браузер используют общую очередь одного исполнителя. Модели работают локально; тестовые ответы доступны только в явно выбранном режиме `mock`.

Это интеграция текущего профиля, который проверяет один сигнал: наличные видны на столе после исчезновения человека из наблюдаемой рабочей зоны. Действия со счётчиком, перенос в шкаф, другой ракурс и расширение правил остаются в этапах 3–5 [единого плана](PROJECT_PLAN.md). Соединение с сайтом не добавляет модели новые способности.

## Запуск на ноутбуке Данияра

В PowerShell из корня репозитория:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\real.ps1 -Install -StartModels
```

Первый запуск устанавливает совместные зависимости в `.venv-app`. Рабочая исследовательская `.venv` не изменяется. Pillow закреплён на 11.3.0, PyAV — на 16.0.1. Веса должны быть предварительно скачаны согласно [инструкции анализатора](../analyzer/README.md).

Для последующих запусков:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\real.ps1 -StartModels
```

Скрипт запускает только отсутствующие модельные серверы: 2B на порту 8080 с контекстом 2048, 4B на 8081 с контекстом 4096. Затем проверяет здоровье и имена обеих моделей. Занятый чужим процессом порт не освобождается автоматически. `-CheckOnly` проверяет готовность без запуска приложения.

Откройте <http://127.0.0.1:8000>. Выберите MOV и дождитесь результата. Один сервер отдаёт и страницу, и API; отдельная сборка frontend не нужна. Остановка приложения — Ctrl+C; модели остаются загруженными. Не запускайте несколько приложений для одновременного анализа на одной GPU.

Видео, база заданий и ключ находятся в `backend/.local/real`, вне Git. Исходные наблюдения анализатора — в `runs/stage3/service-*`. Не отправляйте эти каталоги в репозиторий.

## Что проверяет соединение

1. Перед разрешением загрузки сервер проверяет обе модели, а не только импорт Python-модуля.
2. Файл сохраняется отдельно для каждого задания. Сервер возвращает номер, продолжая отвечать на запросы.
3. Исполнитель передаёт файл анализатору. Время очереди уменьшает доступный бюджет обработки.
4. Сервер проверяет JSON и JPEG перед статусом `done`. Техническая ошибка или незавершённая проверка дают `failed` без вердикта «нарушений нет».
5. Сайт показывает исходные объяснения, таймкоды, кадры и ссылку на официальный источник. Текущий список проверок передаётся отдельно через `/ui/session`; контракт жюри не изменён.
6. Обновление страницы запрашивает прежнее задание. Оно не создаёт повторный анализ. Для плеера можно заново выбрать исходный файл локально.

Набор правил не сохраняется в старых заданиях, поэтому восстановленный отчёт прямо сообщает, что его исторический объём проверок недоступен. Он не получает автоматически профиль более новой версии сервера. Время обработки восстановленного отчёта также не угадывается.

## Проверка API

```powershell
.\.venv-app\Scripts\python.exe -m backend.check_api --expect-mode real --key-file .\backend\.local\real\api-key.txt --video 'C:\Videos\example.mov'
```

Проверка измеряет общий срок от начала отправки до получения и проверки результата, включая JPEG. Лимит — 300 секунд. Сам сервер отсчитывает свой внутренний лимит после приёма multipart; он не заменяет внешний замер. Успешный короткий ролик не подтверждает скорость всех записей, другой сети или очереди.

## Проверенный локальный результат

Проверки проведены 18 октября 2026 года на знакомых исходных роликах с заранее загруженными моделями. Это проверка интеграции и сохранения прежнего поведения, а не независимая оценка качества.

| Путь | Вход | Результат | Время |
| --- | --- | --- | --- |
| Сайт | Видео 26 | Одно событие в 19,7667 с, три настоящих кадра, полный текст и ссылка | 48 с по таймеру страницы |
| API | Видео 26 | `done`, `violation`, одно событие; JPEG и времена совпадают с оригиналами анализатора | 48,02 с |
| API | Видео 25 | `done`, `no_violation` по текущей проверке | 80,52 с |
| API | Видео 14, длинная запись | `done`, `no_violation` по текущей проверке | 247,33 с |

API-замеры включают передачу по loopback, ожидание, получение JSON и проверку кадров. Они не измеряют скорость интернета жюри. Время 19,7667 с — подтверждение текущего правила, а не установленная секунда ухода человека.

Проверены: отказ без ключа и с неверным ключом (401), неизвестное задание (404), повреждённый MOV (422), стабильность повторного GET, совпадение сохранённого файла с загруженным и совпадение трёх JPEG с исходными кадрами. В браузере проверены увеличение, переключение кадров, переход к событию и восстановление того же задания после обновления страницы. После остановки и повторного запуска приложения все три API-ответа совпали с сохранёнными, а браузер восстановил прежнее задание. Это проверка перезапуска приложения, не полной перезагрузки Windows. Локальные протоколы и снимки находятся в исключённой из Git папке `runs/stage6/`.

Автоматические проверки: 464 теста анализатора и запуска (460 прошли, 4 пропущены на Windows), 208 backend-тестов, 61 frontend-тест. Они проверяют поведение программы, но не заменяют измерение распознавания на видео.

## Внешний доступ и оставшиеся проверки

Порядок запуска временного HTTPS-адреса и обращения с записями описан в [PUBLIC_ACCESS.md](PUBLIC_ACCESS.md). Для настоящего режима сначала устанавливаются совместные зависимости через `real.ps1`, затем явно выбирается `public.ps1 -Mode real`. По умолчанию публичный скрипт запускает демонстрационный `mock`.

Временный внешний HTTPS-адрес проверен из браузера и API-клиента. Пользователь подтвердил открытие страницы с готовым сервером с другого устройства в ответ на просьбу проверить другую сеть. Это подтверждение пользователя, не отдельный автоматический замер с того устройства.

Через внешний API отправлен только нейтральный MOV с тестовым изображением. Получены `job_id`, `processing` и итоговый `failed` за 37,08 с; 3,63 с заняли передача и приём. Проверены 401, 404 и 422. Модели действительно выполнили локальные запросы: на изображении без рабочего стола ответ локализации оказался противоречивым (`visible=no` вместе с координатами), поэтому анализатор сообщил `IncompleteAnalysisError`. Сервер не подменил это ответом `no_violation`. Протокол — `runs/stage6/public-neutral-v1`.

Это подтверждает внешний транспорт и передачу ошибки анализа, но **не успешный полный анализ кассового видео через внешний API**. Банковские записи для проверки туннеля не отправлялись. Допустимый маршрут таких записей нужно согласовать согласно ограничениям кейса. Поведение локализации на неподходящем входе сохранено как пример для доработок этапа 3, без изменения правил в ходе интеграции.

Тот же нейтральный ролик дополнительно отправлен через внешний сайт. За 35 с страница показала «Не удалось завершить анализ» и явно указала отсутствие заключения; карточки выдуманных нарушений не появились. Снимок сохранён в `runs/stage6/public-neutral-failed.png`. Текущий адрес и состояние процессов находятся только в локальном `runs/stage6/checkpoint.json`; временный URL не закрепляется как постоянный адрес сдачи.

До завершения этапов 6–7 нужно подтвердить успешный внешний анализ по согласованному маршруту, обработку очереди при одновременных заданиях, несколько событий в реальном ответе, окончательный набор правил и полный срок для пяти и более новых видео. Финальная конфигурация должна пройти проверку после перезагрузки. Публикацию в GitHub и PR выполняет Данияр.
