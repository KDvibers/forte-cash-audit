# Шаблон замеров времени и качества

Этот файл остаётся пустым шаблоном в Git. Заполняйте отдельную локальную копию
после проверки на выбранном наборе видео. Техническая проверка `mock` и оценка
реальной модели — разные серии; не объединяйте их результаты.

## 1. Создать локальную копию

Из корня репозитория в PowerShell:

```powershell
$evaluationRoot = Join-Path (Get-Location).Path 'review\evaluation'
New-Item -ItemType Directory -Path $evaluationRoot -Force -ErrorAction Stop | Out-Null
$runName = (Get-Date -Format 'yyyyMMdd-HHmmss') + '-' + [guid]::NewGuid().ToString('N')
$runDir = Join-Path $evaluationRoot $runName
New-Item -ItemType Directory -Path $runDir -ErrorAction Stop | Out-Null
$reportPath = Join-Path $runDir 'MEASUREMENTS.md'
Copy-Item -LiteralPath '.\docs\submission\MEASUREMENTS.template.md' `
    -Destination $reportPath -ErrorAction Stop
Write-Output $reportPath
```

Каждый запуск создаёт новую папку и не перезаписывает предыдущий отчёт.
`review/` исключён из Git. Допустимое другое место —
`backend/.local/submission/`, также исключённое из Git.
Заполненные отчёты, разметка, соответствие идентификаторов исходным файлам,
кадры и результаты анализа остаются только в этих локальных каталогах.
Не добавляйте их через `git add -f` и не переносите в `docs/`.
API-ключи, cookie и токены в отчёт не записываются.

В таблицах используйте нейтральные идентификаторы вроде `video-001`.
Имена исходных файлов и пути к ним храните в отдельном локальном соответствии.
Для сдачи готовится только разрешённая к передаче сводка; исходная разметка
и содержимое записей не должны появляться в публичном репозитории.

## 3. Как измерять время

`backend.check_api` с `--expect-mode real` и явно указанным разрешённым MOV
проверяет один полный API-запрос. Формат ответа описан в
[контракте API](../API_CONTRACT.md); параметры утилиты доступны через
`.\.venv-app\Scripts\python.exe -m backend.check_api --help`.
Файл ключа передаётся через `--key-file`.
Не запускайте реальную запись по внешнему адресу до согласования маршрута.

| Поле таблицы | Что входит |
| --- | --- |
| `t_upload_accept`, с | От начала `submit` до получения `job_id`: чтение файла, передача и приём сервером, ответ POST. |
| `t_wait`, с | От получения `job_id` до конца проверки ответа: оставшееся ожидание очереди, обработка, опрос GET, передача результата и проверка контракта/JPEG. Это не чистое время модели. |
| `t_total`, с | `t_upload_accept + t_wait`, от начала отправки до завершения проверки ответа. Если запрос завершился ошибкой, это время попытки, а не время успешного результата. |
| `t_inference`, с | Только инструментально измеренный участок вызова модели, с указанными границами. Без такого измерения — `Н/Д`, не `0` и не `t_wait`. |
| Время готовности, с | Запуск сервера и загрузка модели отдельно. Ожидание `/health` выполняется до начала `t_total` в `check_api`. |

Опрос добавляет задержку до следующего GET. Часть работы может начаться до
получения клиентом `job_id`; не используйте эти интервалы как точное разбиение
внутренних стадий сервера. Для разделения очереди, извлечения кадров и модели
нужны отдельные измерения на сервере.

В консоли `check_api` этим значениям соответствуют строки «Передача и приём
файла», «Ожидание и проверка ответа», «Всего от отправки до проверки ответа».
При сбое загрузки печатается только «Время попытки отправки»; отсутствующие
интервалы записывайте как `Н/Д`.

Код выхода `0` означает технически корректный ответ, но не правильный вердикт
и не соблюдение пяти минут. Утилита ожидает задание до 330 секунд после приёма;
для критерия кейса отдельно проверяйте **успешный полный результат за ≤ 300 с**.
Фиксируйте также `t_wait`, чтобы показать обе границы измерения. Точное начало
отсчёта лимита нужно уточнить у организаторов; `t_total` учитывает и загрузку.

`check-public.ps1` выполняет несколько проверок и два последовательных задания
на нейтральных видео. Его итоговая длительность — время всей проверки доступа,
а не одного ролика. Результаты `mock` из [этапа 9](../PUBLIC_ACCESS.md#проверка-этапа-9)
подтверждают передачу данных и не заменяют замеры реального анализа.

## 4. Попытки и полное время

Записывайте каждую попытку, в том числе ошибки и превышение времени.
`processing`, `done`, `failed` — единственные статусы API.
Если статус получить не удалось, пишите `Н/Д`, а причину — в колонке сбоя.
У `failed` и незавершённой попытки нет итогового вердикта.

| ID попытки | ID видео / группа дубликатов | Набор | Режим | Длительность видео, с / размер, байт | Условия: первый / повтор; заданий впереди | Последний статус API | Причина сбоя или `нет` | `t_upload_accept`, с | `t_wait`, с | `t_total`, с | `t_inference`, с / границы | Полный успешный ответ ≤ 300 с: да / нет / Н/Д |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| — | — | — | — | — | — | — | — | — | — | — | — | — |

Для попытки с техническим сбоем условие «полный успешный ответ ≤ 300 с» не
выполнено, даже если сбой наступил быстро. `Н/Д` используется, когда время или
завершение не удалось установить. Не исключайте такие попытки из сводки.
Два одновременных задания проверяйте отдельной серией: один GPU-исполнитель
создаёт ожидание в очереди, а успешный одиночный запуск не гарантирует тот же
результат при нагрузке.

## 5. Вердикт и ручная проверка доказательств

Эталон фиксируется до просмотра ответа модели. Если исходная разметка спорная
или недостаточная, отметьте это в локальном отчёте и исключите такой пример
из расчёта качества с явным указанием количества и причины. Не меняйте эталон,
чтобы он совпал с ответом системы.

| ID попытки | Эталон: `violation` / `no_violation` | Вердикт API при `done` | Вердикт верен: да / нет / не оценён | Событий в эталоне / в ответе | Ручная оценка событий, времени, кадров и источника | Проверяющий / замечание |
| --- | --- | --- | --- | --- | --- | --- |
| — | — | — | — | — | — | — |

По каждому событию заполните отдельную строку. Поля ниже — форма ручной оценки,
не новые обязательные поля API. Нормативная ссылка в текущем контракте находится
в `description`.

| ID попытки / события | Эталонное действие и интервал, с | `type` / `timecode_sec` ответа | Событие подтверждено / пропущено / лишнее | Ошибка времени, с; соответствует заранее выбранному допуску | 1–3 JPEG: декодируются, из этого видео, время соответствует, действие видно | Нормативный источник в `description`: существует, пункт проверен, применим к видимому действию | Кто проверил / замечание |
| --- | --- | --- | --- | --- | --- | --- | --- |
| — | — | — | — | — | — | — | — |

Корректный JPEG не доказывает, что кадр взят из исходного видео или подтверждает
нарушение. Это проверяется отдельно по локальному оригиналу. Для пропущенного
события поля ответа — `Н/Д`; для лишнего отсутствует эталонный интервал.
Один прогноз сопоставляется максимум с одним эталонным событием и наоборот.
Дубликаты одного события в ответе не считаются несколькими правильными находками.
Выбранный командой допуск времени — внутренняя метрика, не официальное
правило начисления баллов жюри; саму ошибку времени записывайте отдельно.

## 6. Сводка серии

Заполняйте только после завершения всех запланированных попыток. Не объединяйте
первый запуск, повторные запуски, нагрузочную серию и разные модели в один
непояснённый средний показатель.

| Показатель | Значение / основание |
| --- | --- |
| Всего попыток / уникальных видео / независимых групп | — |
| `done` / `failed` / не завершены или статус неизвестен | — |
| Попыток с полным успешным ответом ≤ 300 с / всех попыток | — |
| `t_total` успешных: минимум / медиана / максимум; число замеров | — |
| Число реальных отложенных видео с однозначным эталоном | — |
| Из них `done` / технические сбои / не завершены | — |
| TP / FP / FN / TN среди `done` с однозначным эталоном | — |
| Precision / Recall / Accuracy; числители и знаменатели | — |
| Эталонных событий / совпадений / лишних / пропущенных среди оценённых ответов | — |
| Проверенных кадров / кадров с неверным происхождением, временем или содержанием | — |
| Проверенных нормативных ссылок / ошибочных или неприменимых | — |
| Спорных эталонов, исключённых из качества, и причины | — |
| Основные ограничения; что пока не измерено | — |

Для вердикта по видео положительный класс — `violation`:

- TP: эталон и ответ `violation`; TN: оба `no_violation`.
- FP: эталон `no_violation`, ответ `violation`; FN: наоборот.
- Precision = TP / (TP + FP); Recall = TP / (TP + FN).
- Accuracy = (TP + TN) / (TP + FP + FN + TN).
- При нулевом знаменателе результат — `Н/Д`; рядом всегда приводятся количества.

Эти формулы применяются только к `done` в реальном режиме на однозначно
размеченном отложенном наборе. Ошибки обработки не превращаются в TN или
`no_violation`: их количество и доля среди всех попыток показываются отдельно.
Для общего результата дополнительно укажите долю всех однозначно размеченных
отложенных видео этой реальной серии, по которым получен корректный вердикт,
с явным учётом невыданных ответов в знаменателе.
При повторных запусках заранее выберите один запуск на видео для основного
расчёта; разброс повторов покажите отдельно, не выбирая наиболее удачный ответ.

Верный итоговый вердикт не означает, что все события, времена и доказательства
верны. Оценку событий и кадров публикуйте отдельно от точности вердикта.
Малое число роликов, просмотренный ранее набор и неполная разметка ограничивают
выводы; отсутствие ошибок в небольшой серии не доказывает 100% качество.
