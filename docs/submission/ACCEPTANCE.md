# Совместная проверка перед сдачей

Касымбек проверяет приложение, API и доступ. Данияр проверяет анализатор,
модель, наблюдаемые события и нормативные ссылки. Обе стороны подписывают
итог после проверки на ноутбуке Данияра. Дедлайн команды: **18 октября
2026 года, 12:00, Asia/Qyzylorda**.

Это порядок будущей приёмки, а не отчёт о пройденных испытаниях. Пустая
графа «Результат» означает, что сценарий ещё не подтверждён. Успех в `mock`
подтверждает работу приложения, но не качество модели и не скорость `real`.

Обновление 18.10.2026: анализатор и приложение уже объединены. Данияр подтвердил
внешнюю загрузку правильного видео, отчёт, кадры и сохранение после обновления.
44,988 с измерены на сервере; полного клиентского замера этой проверки нет.
Ниже остаётся порядок повторной приёмки окончательной версии после этапов 4–5,
а не требование заново доказывать уже записанные исторические результаты.
Актуальные подтверждения и отказы — в [протоколе](../FUNNEL_INTEGRATION_STATUS.md).

Связанные документы: [состав пакета](README.md), [архитектура](ARCHITECTURE.md),
[замеры](MEASUREMENTS.template.md), [готовность к сдаче](CHECKLIST.md),
[передача жюри](JURY_HANDOFF.template.md). Поля ответа определены в
[контракте API](../API_CONTRACT.md).

## 1. Зафиксировать версию и подготовить материалы

Перед совместным прогоном:

1. Оба участника записывают проверяемый коммит приложения и коммит анализатора.
   После объединения изменений используют один согласованный коммит.
   Локальные изменения отдельно перечисляют в протоколе.
2. Сверьте включённый `analyzer/service.py`, именованный параметр `budget_sec`,
   команды запуска, версии моделей и настройки с проверяемой версией.
   Рабочий порядок запуска: [REAL_RUNBOOK.md](../REAL_RUNBOOK.md).
3. Зависимости совместной `.venv-app` согласованы: прежний конфликт Pillow
   устранён. Версии рабочего состава — в [COMPONENTS.md](../COMPONENTS.md).
   При изменениях повторите диагностику; не устанавливайте пакеты поверх
   рабочего окружения наугад.
4. Выберите разрешённые учебные видео с ручной разметкой: без нарушений, с одним
   нарушением, с несколькими событиями. До просмотра ответа модели запишите
   ожидаемые типы, моменты событий, допустимую погрешность таймкода и источник
   каждого правила. Непонятный случай отметьте как спорный, а не как эталон.
   Выбранная командой погрешность — внутренняя метрика, не официальный допуск жюри.
5. Для оценки качества выделите видео, не использованные для подбора правил
   и настроек. Одинаковые копии видео должны оставаться в одной группе.
   Если независимых роликов нет, так и укажите: качество на новых данных
   ещё не проверено.

Разметку, видео, ответы с кадрами и заполненные протоколы храните локально
в `review/evaluation/` или `backend/.local/submission/` — оба каталога исключены
из Git. Указывайте условные ID
роликов вместо фамилий и иных сведений о людях. В репозитории остаются только
пустые шаблоны и общие инструкции; ключ API, веса, исходные записи и кадры
не добавляются в коммит.

## 2. Сначала проверить приложение в mock

Команды выполняются из корня репозитория, в PowerShell 5.1 или новее.
Нужны Python 3.12 x64 и Node.js 22+ для frontend-тестов.

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\check.ps1 -Install
if ($LASTEXITCODE -ne 0) { throw 'Самопроверка не прошла. Сначала исправьте ошибку.' }
```

При повторной проверке готового окружения `-Install` не нужен. Эта команда
запускает тесты и отдельный локальный HTTP-прогон с нейтральным видео.
Запишите дату, коммит, число тестов и код завершения текущего запуска:
исторические результаты предыдущих этапов не заменяют проверку новой сборки.

Для ручных сценариев запустите:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\demo.ps1
```

Откройте вручную <http://127.0.0.1:8000>, используйте
`backend/.local/demo/sample.mov`. События и кадры в этом режиме синтетические.
Дополнительные сценарии запускаются **по одному**, после Ctrl+C в окне
предыдущего сервера:

```powershell
# Два альтернативных запуска; сначала завершите первый, затем запускайте второй.
powershell -ExecutionPolicy Bypass -File .\scripts\demo.ps1 -Scenario clean -DelaySeconds 2
powershell -ExecutionPolicy Bypass -File .\scripts\demo.ps1 -Scenario error -DelaySeconds 2
```

После смены сценария начните новую проверку на странице: восстановленный
старый отчёт относится к предыдущему заданию. Подробности запуска и выбора
другого свободного порта — в [руководстве демонстрации](../DEMO_GUIDE.md).
Не завершайте чужие процессы, чтобы освободить порт.

## 3. Подключить real и проверить локально

Анализатор и совместимое окружение уже подключены; этот раздел используется
для повторной проверки выбранной окончательной версии. Успех прежней версии
не заменяет проверку последующих изменений. Сервис может быть временно остановлен.

1. Данияр запускает модель своей проверенной командой, подтверждает работу
   на RTX 5070 и передаёт нужные настройки окружения. Сервис анализа использует
   одного исполнителя; модель должна повторно использоваться между заданиями.
2. Укажите путь к подготовленному совместимому окружению. Следующие команды
   не устанавливают пакеты и не запускают модель:

```powershell
$realVenv = Read-Host 'Путь к подготовленному окружению приложения и анализатора'
$realPython = Join-Path $realVenv 'Scripts\python.exe'
if (-not (Test-Path -LiteralPath $realPython)) { throw 'Не найден Python этого окружения.' }
powershell -ExecutionPolicy Bypass -File .\scripts\doctor.ps1 -Mode real -VenvPath $realVenv -DataDir backend\.local\acceptance-real
if ($LASTEXITCODE -ne 0) { throw 'Диагностика real не пройдена. Устраните указанные блокеры.' }
```

Диагностика соответствует текущей архитектуре проекта, включая локальный
сервис модели. Если Данияр изменит эту архитектуру, сначала согласуйте и
обновите диагностику вместе с интеграцией. Текущая проверка готовности включает
`check_ready()` обеих моделей с ожидаемыми именами; она не подтверждает качество
или успешное завершение следующего анализа.

3. Откройте отдельное окно PowerShell для локального сервера и повторно задайте
   `$realVenv`. Убедитесь, что это окно не содержит настроек публичного запуска
   или старого тестового профиля. Сохраните требуемые настройки модели Данияра.
   Для этого прогона используйте отдельный каталог данных:

```powershell
$realVenv = Read-Host 'Путь к согласованному окружению'
$env:CASH_AUDIT_DATA_DIR = Join-Path (Get-Location) 'backend\.local\acceptance-real'
powershell -ExecutionPolicy Bypass -File .\backend\start.ps1 -Mode real -VenvPath $realVenv -Port 8000
```

Команда не содержит `-Install` и не меняет зависимости. Если задан
`CASH_AUDIT_API_KEY`, сервер использует его вместо ключа из файла: заранее
договоритесь об одном способе и храните совпадающий ключ в локальном закрытом
файле. Значение ключа в командную строку и протокол не вставляйте.

4. Во втором окне проверьте один разрешённый MOV через API:

```powershell
$realVenv = Read-Host 'Путь к согласованному окружению'
$realPython = Join-Path $realVenv 'Scripts\python.exe'
$videoPath = Read-Host 'Полный путь к разрешённому учебному MOV'
$keyFile = Read-Host 'Путь к файлу ключа текущего сервера (обычно backend\.local\acceptance-real\api-key.txt)'
& $realPython -m backend.check_api --base-url http://127.0.0.1:8000 --expect-mode real --video $videoPath --key-file $keyFile
$checkExit = $LASTEXITCODE
Write-Host "Код проверки: $checkExit"
```

Код `0` означает успешный ответ по контракту, `2` — `failed`, `1` — ошибку
проверки или связи. Даже код `0` не подтверждает правильность найденного
нарушения: содержание проверяют оба участника по разметке и исходным кадрам.
`--expect-mode real` останавливает проверку до отправки файла при другом режиме.

5. Повторите загрузку того же разрешённого видео через интерфейс локального
   сервера. API-задания и браузерные задания разделены: результат API-клиента
   не должен появиться в браузере как его собственная проверка. Для сравнения
   выполните два отдельных прогона и запишите оба в таблицу замеров.

## 5. Измерить время и подтвердить внешний маршрут

Для каждого реального прогона заполните [шаблон замеров](MEASUREMENTS.template.md).
В кейсе указан предел **5 минут**. Чтобы не скрыть задержки, записывайте:

- начало отправки видео клиентом;
- получение `job_id` — передача и приём файла уже завершились;
- получение клиентом полного `done` или `failed`;
- ожидание очереди и собственно анализ, если эти интервалы доступны в локальной
  диагностике; если нет — оставьте «не измерено»;
- время запуска модели и прогрева отдельно от времени задания.

`check_api` печатает передачу и приём, ожидание и проверку ответа, а также
общее время от начала отправки до проверенного ответа. Он начинает измерение
после ожидания готовности сервера; это не замер запуска модели. Опрос примерно
раз в секунду даёт дополнительную задержку обнаружения готового ответа.
Внутренний таймаут сервера сам по себе не доказывает соблюдение пяти минут.
Для результата жюри оценивайте полный клиентский путь, включая очередь;
загрузку и внутренние части показывайте отдельно.

Внешний прогон выполняйте по [инструкции внешнего доступа](../PUBLIC_ACCESS.md):

```powershell
# После запуска public.ps1 в другом окне:
$publicUrl = Read-Host 'Текущая HTTPS-ссылка'
powershell -ExecutionPolicy Bypass -File .\scripts\check-public.ps1 -BaseUrl $publicUrl -ExpectMode mock -KeyFile .\backend\.local\public-mock\api-key.txt
```

Для P3 команда применяется к уже запущенному согласованному `real`:
укажите `-ExpectMode real`, ключ `backend/.local/public-real/api-key.txt`
и `-VenvPath` подготовленного окружения. Она сама создаёт нейтральные
синтетические видео. Эти проверки не заменяют ручной показ в браузере и
проверку с другого устройства через другую сеть.

Через Cloudflare проходят видео и кадры. До подтверждения допустимости
такого маршрута организаторами используйте во внешних проверках **только
нейтральные синтетические MOV**. Если маршрут не разрешён, P4 заблокирован
до выбора согласованного размещения. Покупка домена сама по себе это
ограничение не устраняет.

## Условие готовности

Команда готова к реальной сдаче, когда завершены локальная интеграция,
проверка событий и источников, замеры полного времени и согласованный внешний
доступ. Все обязательные сценарии имеют записи результата, а ограничения
указаны в [материалах для жюри](JURY_HANDOFF.template.md). Дополнительный
сценарий R9 оценивает запас устойчивости; не выдавайте его за профиль нагрузки,
официально заданный организаторами.

При оставшемся блокере не переключайте финальную ссылку на `mock` незаметно.
Запишите, что именно не готово, кто исправляет и какой повторный прогон нужен.
