# Архитектура Forte Audit

Состояние документа: **18 октября 2026 года, объединённый real-сервис**.
Касымбек отвечает за интерфейс и сервер приложения, Данияр — за анализатор.
Интерфейс, API, очередь и `analyzer/service.py` соединены. Настоящие результаты
проверены в условиях [протокола интеграции](../FUNNEL_INTEGRATION_STATUS.md).
Включено одно условное правило; полная приёмка сервиса и качество на новых
видео не подтверждены. [Семь этапов проекта](../PROJECT_PLAN.md) сохраняются:
1–2 выполнены, 3–5 частичны. Основной внешний пользовательский путь этапа 6
подтверждён для текущего профиля; финальные проверки версии остаются этапом 7.

## Как проходит проверка

1. Пользователь выбирает MOV в интерфейсе либо отправляет файл через API.
   Интерфейс начинает загрузку автоматически после проверки допустимого файла.
2. FastAPI проверяет доступ, размер и расширение; сохраняет файл в отдельную
   папку задания. Проверка контейнера и декодирование первого кадра отсекают
   явно повреждённые файлы. Целостность всего видео этим не доказывается.
3. Сервер записывает задание в SQLite и возвращает `job_id`. Клиент опрашивает
   статус; HTTP-запрос загрузки не ждёт завершения анализа.
4. Один постоянный процесс последовательно получает задания. В `real` он
   вызывает `analyzer.service.analyze_video(video_path, budget_sec=...)`
   с абсолютным локальным путём и оставшимся бюджетом времени. Анализатор
   выбирает исходные кадры, обращается к двум локальным моделям, применяет
   временное правило и подготавливает настоящие JPEG. В явно выбранном `mock`
   вместо этого возвращается синтетический пример.
5. Сервер проверяет формат ответа и JPEG-кадры, сохраняет результат и выставляет
   `done`. Исключение анализатора, неверный формат или таймаут дают `failed`.
6. Интерфейс показывает вердикт, события, объяснения, таймкоды и кадры. Локальный
   исходный файл используется плеером для перехода к событию, если браузер
   поддерживает его кодек. При недоступном плеере отчёт и кадры остаются доступны.

## Компоненты и границы ответственности

| Компонент | Реализация и назначение |
| --- | --- |
| Интерфейс | `frontend/index.html`, CSS и обычный JavaScript без сборки. `app.js` управляет загрузкой и запросами; `results.js` показывает отчёт; `recovery.js` сохраняет метаданные последней проверки. Внешние шрифты и CDN не нужны. |
| HTTP-приложение | `backend/main.py`: выдача интерфейса, публичный API, браузерные маршруты, приём видео и ограничения запросов. |
| Координатор | `backend/service.py`: очередь, один исполнитель, таймауты, сохранение результата и очистка данных. `backend/store.py`: SQLite. |
| Исполнитель | `backend/worker.py`: отдельный процесс с каналом связи с координатором. Импортирует функцию анализатора один раз и повторно вызывает её. |
| Проверка входа и ответа | `backend/validation.py`: MOV и первый читаемый кадр; схема результата, числовые отметки времени, корректные JPEG. |
| Реальный анализатор | `analyzer/service.py`: `analyze_video`, проверка моделей `check_ready`, область проверки `describe_scope`, контроль завершения и экспорт результата. `observe.py` получает наблюдения, `rules.py` связывает их во времени, `rule_catalog.py` хранит правила и условные нормативные ссылки. |
| Локальные модели | Qwen3-VL-2B на `127.0.0.1:8080` проверяет деньги в выбранной области; Qwen3-VL-4B на `127.0.0.1:8081` выбирает рабочую поверхность и оценивает присутствие человека. Обе работают через отдельные `llama-server` на том же ноутбуке. |
| Внешний доступ | `scripts/funnel-real.ps1` и `backend/public_funnel.py`: Tailscale Funnel, приложение на `127.0.0.1:8020`, данные `backend/.local/funnel-real`. TLS завершается на ноутбуке, где работает backend. |

Сервер запускается с одним Uvicorn worker и одним процессом анализа.
Операционная блокировка запрещает двум экземплярам приложения совместно
использовать один каталог данных; отдельная блокировка real запрещает два
анализатора из одной рабочей копии даже с разными каталогами данных.
По умолчанию допускаются суммарно два
незавершённых задания или зарезервированные загрузки, включая активный анализ;
это не два параллельных GPU-исполнителя. Переполненная очередь возвращает 429.

Веса остаются загруженными в двух локальных `llama-server` между заданиями.
Backend не загружает их заново на каждое видео. Один исполнитель анализа
обращается к этим серверам последовательно; два модельных процесса не означают
два параллельных задания. `scripts/real.ps1 -StartModels -CheckOnly` запускает
только отсутствующие модели и проверяет обе роли. Остановка приложения через
Ctrl+C не останавливает модельные серверы. Сторонние исследовательские процессы
не управляются блокировкой приложения и не должны конкурировать за GPU.

## Два способа доступа

| Клиент | Маршруты | Проверка доступа и принадлежность задания |
| --- | --- | --- |
| Прямой клиент API | `POST /api/v1/analyze`, `GET /api/v1/jobs/{job_id}` | Заголовок `X-API-Key`. Все такие задания относятся к общему владельцу `api`. Владельцы одного ключа могут запросить API-задание, если знают его ID. Это не отдельные пользовательские аккаунты. |
| Браузер | `GET /ui/session`, `POST /ui/analyze`, `GET /ui/jobs/{job_id}`, `GET /ui/recovery/{upload_id}` | Анонимная HttpOnly cookie, проверка Origin и CSRF для загрузки. Задание принадлежит конкретной браузерной сессии. API-ключ в JavaScript не передаётся. |
| Диагностика | `GET /health` | Сообщает режим и состояние исполнителя; не возвращает видео или результаты. |

Браузерная сессия не даёт читать задания публичного API, а API-ключ не открывает
браузерные задания. Cookie устанавливается с `SameSite=Strict`, а при публичном
HTTPS-запуске — также с `Secure`. В SQLite хранится хеш значения cookie.
Сессия действует 24 часа и продлевается при открытии `/ui/session`.

Сам интерфейс доступен любому посетителю публичной ссылки. Cookie, Origin и
CSRF защищают связь с собственной сессией, но не заменяют вход по паролю.
API-ключ хранится отдельно от исходного кода и передаётся жюри закрытым способом.

## Формат результата и смысл проверки

Публичные статусы: `processing`, `done`, `failed`. Ожидание очереди также
отображается как `processing`. Успешные вердикты: `violation` и `no_violation`.
Техническая ошибка не получает вердикт «нарушений нет».

Включённый сигнал: наличные видны на столе после исчезновения человека из
наблюдаемой рабочей зоны. Это основание для ручной проверки, а не установленный
юридический факт. Связь с пунктом 20 правил НБРК № 231 условная: принадлежность
денег и факт их предыдущего приёма этим сигналом не установлены.
`no_violation` относится только к выполненной проверке выбранных кадров,
а не ко всем требованиям кассовой дисциплины. При недостаточной полноте
отрицательный результат не публикуется.

Проверка снятой верхней одежды реализована, но отключена в каталоге правил.
Загрузка/извлечение денег из счётчика и перенос в шкаф остаются экспериментами.
Их наличие в исследовательском коде не расширяет производственный вердикт.
Подробные условия и ограничения: [RULES.md](../RULES.md).

Событие содержит `type`, `timecode_sec`, `description` и 1–3 элемента
`evidence_frames`. Кадр содержит `timestamp_sec` и JPEG в `image_base64`.
Нормативная ссылка передаётся внутри `description`; отдельное обязательное поле
источника или закрытый перечень типов событий интерфейс не добавляет.
Точная схема описана в [контракте API](../API_CONTRACT.md).

Валидация проверяет структуру, согласованность вердикта со списком событий,
конечные неотрицательные таймкоды и декодируемость JPEG. Она **не устанавливает**,
что изображение действительно извлечено из этого видео, время соответствует
кадру, описанное действие произошло или нормативная ссылка применима.
Анализатор сохраняет реальные временные отметки кадров, проверяет целостность
исходного видео и JPEG перед экспортом. Это защищает происхождение файлов,
но не доказывает правильность распознавания: содержание, время события и
применимость нормы проверяются по оригиналу.
Режим `mock` намеренно использует синтетические события и изображения и явно
обозначается в интерфейсе.

## Хранение и восстановление

В каталоге данных экземпляра находятся `jobs.sqlite3`, `api-key.txt` и
`uploads/<job_id>/source.mov`. JSON результата, включая JPEG в base64,
хранится в SQLite. Для Funnel real используется `backend/.local/funnel-real`,
для отдельного локального real — `backend/.local/real`. Данные демонстрации
и настоящего запуска разделены.
Эти каталоги, веса, исходные записи и материалы просмотра исключены из Git.

По умолчанию завершённые задания и соответствующие загруженные видео удаляются
после 24 часов с момента завершения. Очистка выполняется примерно раз в минуту
при работающем сервере. Это не обещание удаления в точную секунду или защищённого
стирания накопителя; остановленный сервер очистку не выполняет. Диагностические
материалы анализатора в `runs/stage3/service-*` сохраняются отдельно; очистка
backend не распространяется на них. Их хранение и удаление контролирует команда.

Готовые результаты сохраняются при перезапуске. При штатной остановке
незавершённые задания становятся `failed` с внутренней причиной `server_stopped`;
при следующем запуске оставшиеся `processing` становятся `failed` с причиной
`server_restarted`. Автоматического продолжения прерванного анализа нет.

В браузерном `localStorage` хранится одна последняя проверка: идентификаторы,
режим, время и свойства исходного файла. Видео, кадры, описания событий, ключ
API и CSRF туда не записываются. После F5 интерфейс читает существующее задание,
не отправляя видео заново. `X-Upload-ID` позволяет найти принятую загрузку,
даже если ответ с `job_id` потерялся; автоматического повторного POST нет.

Для воспроизведения после восстановления пользователь выбирает исходный файл
повторно. Это локальный выбор без новой загрузки. Сверка имени, размера и даты
изменения помогает выбрать файл, но не доказывает равенство содержимого.
Восстановление требует прежних адреса сайта, браузерной сессии и сохранённого
задания. Новый адрес туннеля не переносит cookie и локальное хранилище.

## Локальная обработка и внешний маршрут

При локальном показе браузер обращается непосредственно к серверу ноутбука.
При внешнем показе: устройство жюри → публичный TCP-ретранслятор Funnel →
Tailscale на ноутбуке Данияра → `127.0.0.1:8020` → локальный анализатор и модели.
TLS начинается у клиента и завершается в Tailscale на том же ноутбуке, где
работает приложение; ретранслятор передаёт зашифрованный поток. После
расшифровки HTTP остаётся на loopback этого ноутбука. Видео не пересылаются
для обработки на ноутбук Касымбека. Модельные порты 8080/8081 не публикуются.

Это локальный AI с внешним сетевым ретранслятором, а не отсутствие сторонней
инфраструктуры. Сетевые метаданные и хранение на диске — отдельные вопросы;
официального одобрения трактовки кейса о зашифрованном транзите команда не
получала. Границы защиты и ссылки на устройство Funnel описаны в
[руководстве Funnel](../FUNNEL_ACCESS.md). Прежний Cloudflare-маршрут —
исторический вариант, не текущий запуск.

По умолчанию принимаются файлы до 100 МиБ; интерфейс получает актуальный
лимит от сервера. Доступ зависит от ноутбука, сети, состояния Funnel и
публичного DNS. Локальное открытие tailnet-имени может идти по частному маршруту.
Видео и кадры не отправляются внешним AI-сервисам; аудио не анализируется,
идентификация людей по лицу не выполняется.

## Модели и текущий профиль анализа

Параметры ниже заданы в `analyzer/service.py`, `analyzer/start_model.ps1`
и `scripts/real.ps1`; это описание реализации, не новый замер.

| Компонент | Текущий профиль |
| --- | --- |
| Деньги | `Qwen3VL-2B-Instruct-Q4_K_M.gguf`, визуальный компонент F16, порт 8080; контекст при запуске скриптом — 2048 токенов. |
| Рабочая зона и присутствие | `Qwen3VL-4B-Instruct-Q4_K_M.gguf`, визуальный компонент F16, порт 8081; контекст — 4096 токенов. |
| Runtime | Локальный llama.cpp `b11669`; для каждой модели один слот, KV-кэш F16, параметры визуальных токенов 1024–1280. Веса повторно используются между заданиями. |
| Выбор кадров | Входные настройки текущего сервиса: интервал 2 с, максимум 80 кадров. Используются исходные временные отметки; шаг и ограничения покрытия сохраняются в отчёте. Уплотнение коротких действий и экспериментальные action-проходы в сервисе выключены. |
| Правило | История присутствия человека и денег на рабочем столе, последовательное подтверждение и группировка эпизодов; неопределённые промежутки не считаются непрерывным событием. |
| Ограничения | Возможны ошибки выбора стола, пропуски коротких действий и неоднозначность мелких денег. При подтверждённом присутствии человека вопросы о деньгах пропускаются только в рамках текущего правила. Пропуск вопроса не означает отсутствие денег. |

Проверки 8B и дообученных детекторов не дали основания включить их в этот
производственный путь. Качество на новых ракурсах, окончательные показатели
ошибок, пик памяти и лицензии поставляемых компонентов требуют итогового аудита.

Отдельные окружения `.venv-app` и `.venv` сохраняют возможность разрабатывать
две части независимо. Но Python worker приложения импортирует `analyzer.service`
в своём окружении: отдельная `.venv` сама по себе не соединяет зависимости.
Совместное окружение `.venv-app` устанавливается по `backend/requirements-real.txt`;
версии согласованы: Pillow `11.3.0`, PyAV `16.0.1`. Отдельная исследовательская
`.venv` сохраняется; worker приложения её автоматически не использует.

## Готовность и время ответа

`/health` с `analyzer_ready=true` в режиме `real` подтверждает готовность
исполнителя и успешного `check_ready()` обеих локальных моделей с ожидаемыми
именами весов. Совместимость функции с именованным `budget_sec` обязательна;
проверка повторяется перед заданиями и в простое. Это не измерение точности
или времени обработки. HTTP 200 у `/health` может сопровождаться `degraded`;
нужны также `mode=real`, `status=ok` и `analyzer_ready=true`.

Внутренний таймаут задания по умолчанию равен 285 секундам. Его отсчёт начинается
при первом входе запроса загрузки в ASGI, до разбора multipart, и включает
приём, сохранение, проверку видео, очередь и анализ. Анализатор получает
не более `min(260, остаток - 5)` секунд; при остатке не более 15 секунд
новый анализ не начинается. Клиентская проверка отдельно требует не более
300 секунд от начала отправки до получения и проверки полного ответа.
DNS, соединение и обратная передача тоже занимают время, поэтому серверный
дедлайн не гарантирует клиентский результат за пять минут.

После таймаута или технической ошибки real новые вызовы блокируются до
проверки моделей и перезапуска: завершение Python-клиента не гарантирует
остановку запроса внутри модели. Отдельный полностью завершённый анализ
с недостаточными визуальными данными может отказать без блокировки следующего
задания; это всё равно `failed`, а не `no_violation`. Порядок восстановления
и проверка простоя моделей: [REAL_RUNBOOK.md](../REAL_RUNBOOK.md).

Внешняя пользовательская загрузка, отчёт, кадры и восстановление после обновления
подтверждены Данияром; 44,988 с — серверное время, без полного клиентского замера.
Для приёмки остаются повтор на окончательной версии, внешний API с полным замером,
воспроизводимый запуск и проверка после перезагрузки, а также
качество событий и нормативных объяснений на новых видео. Конкретные результаты
и отказы фиксируются в [протоколе](../FUNNEL_INTEGRATION_STATUS.md).
Этот документ не подтверждает текущий health после изменений и не закрывает
незавершённые этапы 3–5.
