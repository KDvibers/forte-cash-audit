# Архитектура Forte Audit

Состояние документа: **17 октября 2026 года, подготовка совместной проверки**.
Касымбек отвечает за интерфейс и сервер приложения, Данияр — за анализатор.
Интерфейс, API и служба заданий реализованы. Полный путь проверялся с явно
включённым тестовым анализатором. Рабочая функция `analyzer/service.py`
ещё отсутствует; результат реального анализа и готовность решения к сдаче
этот документ не подтверждает.

## Как проходит проверка

1. Пользователь выбирает MOV в интерфейсе либо отправляет файл через API.
   Интерфейс начинает загрузку автоматически после проверки допустимого файла.
2. FastAPI проверяет доступ, размер и расширение; сохраняет файл в отдельную
   папку задания. Проверка контейнера и декодирование первого кадра отсекают
   явно повреждённые файлы. Целостность всего видео этим не доказывается.
3. Сервер записывает задание в SQLite и возвращает `job_id`. Клиент опрашивает
   статус; HTTP-запрос загрузки не ждёт завершения анализа.
4. Один постоянный процесс последовательно получает задания. В `mock` он
   возвращает синтетический пример. В `real` должен вызывать
   `analyzer.service.analyze_video(video_path)` с абсолютным локальным путём.
5. Сервер проверяет формат ответа и JPEG-кадры, сохраняет результат и выставляет
   `done`. Исключение анализатора, неверный формат или таймаут дают `failed`.
6. Интерфейс показывает вердикт, события, объяснения, таймкоды и кадры. Локальный
   исходный файл используется плеером для перехода к событию, если браузер
   поддерживает его кодек. При недоступном плеере отчёт и кадры остаются доступны.

## Компоненты и границы ответственности

| Компонент | Реализация и назначение |
| --- | --- |
| Интерфейс | `frontend/index.html`, CSS и обычный JavaScript без сборки. `app.js` управляет загрузкой и запросами; `results.js` показывает отчёт; `recovery.js` сохраняет метаданные последней проверки. Внешние шрифты и CDN не нужны. |
| HTTP-приложение | `backend/main.py`: выдача интерфейса, публичный API, браузерные маршруты, приём видео и ограничения запросов. |
| Координатор | `backend/service.py`: очередь, один исполнитель, таймауты, сохранение результата и очистка данных. `backend/store.py`: SQLite. |
| Исполнитель | `backend/worker.py`: отдельный процесс с каналом связи с координатором. Импортирует функцию анализатора один раз и повторно вызывает её. |
| Проверка входа и ответа | `backend/validation.py`: MOV и первый читаемый кадр; схема результата, числовые отметки времени, корректные JPEG. |
| Реальный анализатор | Ожидаемый модуль `analyzer/service.py`, пока не реализован в этой версии репозитория. Он должен выбирать кадры, устанавливать наблюдаемые события, проверять правила и возвращать доказательства. |
| Диагностическая модель | В `analyzer/` уже есть извлечение кадров, клиент локальной модели и диагностический запуск. Их результат ещё не является вердиктом о нарушении. |
| Внешний доступ | `scripts/public.ps1` и `backend/public_tunnel.py`: временный HTTPS-адрес Cloudflare, локальный сервер приложения и отдельные данные `public-mock` / `public-real`. |

Сервер запускается с одним Uvicorn worker и одним процессом анализа.
Операционная блокировка запрещает двум экземплярам приложения совместно
использовать один каталог данных. По умолчанию допускаются суммарно два
незавершённых задания или зарезервированные загрузки, включая активный анализ;
это не два параллельных GPU-исполнителя. Переполненная очередь возвращает 429.

Постоянный процесс позволяет повторно использовать состояние анализатора,
но сам backend не загружает веса и не гарантирует их повторное использование.
В текущем диагностическом варианте веса находятся в отдельном локальном
`llama-server`. Окончательный жизненный цикл модели нужно подтвердить при интеграции.

## Два способа доступа

| Клиент | Маршруты | Проверка доступа и принадлежность задания |
| --- | --- | --- |
| Прямой клиент API | `POST /api/v1/analyze`, `GET /api/v1/jobs/{job_id}` | Заголовок `X-API-Key`. Все такие задания относятся к общему владельцу `api`. Владельцы одного ключа могут запросить API-задание, если знают его ID. Это не отдельные пользовательские аккаунты. |
| Браузер | `GET /ui/session`, `POST /ui/analyze`, `GET /ui/jobs/{job_id}`, `GET /ui/recovery/{upload_id}` | Анонимная HttpOnly cookie, проверка Origin и CSRF для загрузки. Задание принадлежит конкретной браузерной сессии. API-ключ в JavaScript не передаётся. |
| Диагностика | `GET /health` | Сообщает режим и состояние исполнителя; не возвращает видео или результаты. |

Браузерная сессия не даёт читать задания публичного API, а API-ключ не открывает
браузерные задания. Cookie устанавливается с `SameSite=Strict`, а при публичном
HTTPS-запуске — также с `Secure`. В SQLite хранится хеш значения cookie.
Сессия действует 24 часа и продлевается при открытии `/ui/session`.

Сам интерфейс доступен любому посетителю публичной ссылки. Cookie, Origin и
CSRF защищают связь с собственной сессией, но не заменяют вход по паролю.
API-ключ хранится отдельно от исходного кода и передаётся жюри закрытым способом.

## Формат результата и смысл проверки

Публичные статусы: `processing`, `done`, `failed`. Ожидание очереди также
отображается как `processing`. Успешные вердикты: `violation` и `no_violation`.
Техническая ошибка не получает вердикт «нарушений нет».

Событие содержит `type`, `timecode_sec`, `description` и 1–3 элемента
`evidence_frames`. Кадр содержит `timestamp_sec` и JPEG в `image_base64`.
Нормативная ссылка передаётся внутри `description`; отдельное обязательное поле
источника или закрытый перечень типов событий интерфейс не добавляет.
Точная схема описана в [контракте API](../API_CONTRACT.md).

Валидация проверяет структуру, согласованность вердикта со списком событий,
конечные неотрицательные таймкоды и декодируемость JPEG. Она **не устанавливает**,
что изображение действительно извлечено из этого видео, время соответствует
кадру, описанное действие произошло или нормативная ссылка применима.
Эти свойства нужно проверять в анализаторе и совместном просмотре исходных видео.
Режим `mock` намеренно использует синтетические события и изображения и явно
обозначается в интерфейсе.

## Хранение и восстановление

В каталоге данных экземпляра находятся `jobs.sqlite3`, `api-key.txt` и
`uploads/<job_id>/source.mov`. JSON результата, включая JPEG в base64,
хранится в SQLite. Данные демонстрации и публичного запуска разделены.
Эти каталоги, веса, исходные записи и материалы просмотра исключены из Git.

По умолчанию завершённые задания и соответствующие загруженные видео удаляются
после 24 часов с момента завершения. Очистка выполняется примерно раз в минуту
при работающем сервере. Это не обещание удаления в точную секунду или защищённого
стирания накопителя; остановленный сервер очистку не выполняет.

Готовые результаты сохраняются при перезапуске. При штатной остановке
незавершённые задания становятся `failed` с внутренней причиной `server_stopped`;
при следующем запуске оставшиеся `processing` становятся `failed` с причиной
`server_restarted`. Автоматического продолжения прерванного анализа нет.

В браузерном `localStorage` хранится одна последняя проверка: идентификаторы,
режим, время и свойства исходного файла. Видео, кадры, описания событий, ключ
API и CSRF туда не записываются. После F5 интерфейс читает существующее задание,
не отправляя видео заново. `X-Upload-ID` позволяет найти принятую загрузку,
даже если ответ с `job_id` потерялся; автоматического повторного POST нет.

Для воспроизведения после восстановления пользователь выбирает исходный файл
повторно. Это локальный выбор без новой загрузки. Сверка имени, размера и даты
изменения помогает выбрать файл, но не доказывает равенство содержимого.
Восстановление требует прежних адреса сайта, браузерной сессии и сохранённого
задания. Новый адрес туннеля не переносит cookie и локальное хранилище.

## Локальная обработка и внешний маршрут

При локальном показе браузер обращается непосредственно к серверу ноутбука.
При внешнем показе маршрут другой: устройство жюри → HTTPS Cloudflare →
туннель → локальное приложение. Затем кадры должны обрабатываться локальной
моделью на ноутбуке Данияра. Внутренний диагностический адрес модели —
`http://127.0.0.1:8080`; его не нужно публиковать как API жюри.

Локальная модель и локальное хранение не означают отсутствие сторонней передачи
при туннеле. TLS завершается на инфраструктуре Cloudflare; исходное видео и
ответ проходят через этот сервис. До согласования такого маршрута для записей
жюри внешний показ проводится только на нейтральных синтетических видео.
Решение о разрешённом маршруте фиксируется отдельно от технической готовности
туннеля. Подготовка и ограничения описаны в
[руководстве внешнего доступа](../PUBLIC_ACCESS.md).

Текущий публичный профиль принимает файлы до 90 МиБ, локальный — до 100 МиБ;
интерфейс получает актуальный лимит от сервера. Временный адрес и доступность
зависят от работающего ноутбука, туннеля и сети. Новый запуск может изменить URL.

автоматически диагностическое Python-окружение или модель.

## Готовность и время ответа

`/health` с `analyzer_ready=true` в режиме `real` подтверждает готовность
исполнителя после импорта вызываемой функции. Это не доказательство загрузки
весов, корректности модели или успешного анализа видео. Требуются проверка
локального сервера модели и полный реальный запрос через API.

Внутренний таймаут задания по умолчанию равен 285 секундам. Его отсчёт начинается
в обработчике сохранения файла, после разбора входного multipart-запроса,
и включает последующую проверку видео, очередь и анализ. Он не охватывает
весь клиентский путь загрузки по сети. Поэтому наличие таймаута не доказывает
выполнение требования результата за пять минут: отдельно измеряется время
от начала отправки клиентом до получения конечного ответа.

Для готовности к сдаче остаются подключение реального модуля, согласование
зависимостей и внешнего маршрута, проверка происхождения кадров, качества
событий и нормативных объяснений, а также полные замеры на ноутбуке Данияра.
Автоматические проверки приложения и нейтральный сетевой показ подтверждают
работу транспортной части; качество анализа кассовых операций ими не измеряется.
