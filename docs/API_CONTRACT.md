# Формат обмена между анализатором, сервером и интерфейсом

Этот документ фиксирует договорённость команды. Публичные маршруты и поля результата взяты из кейса ForteBank; внутренняя функция, организация очереди и маршруты браузера — наши решения реализации. Сервер уже находится в `backend/`; интеграция с реальным анализатором ещё не завершена. Изменения общей схемы согласуются обеими сторонами до реализации.

## Внутренний анализатор: сторона Данияра

Python-модуль: `analyzer/service.py`. Точка входа: `analyze_video(video_path: str) -> dict`.

Сервер передаёт абсолютный путь к уже сохранённому видео на компьютере, где работает анализатор. Анализатор не принимает HTTP-запросы, не создаёт `job_id` и не управляет API-ключами. Вызов блокирует своего исполнителя до получения результата; сервер обязан запускать его вне обработки HTTP-запроса.

При успешной обработке функция возвращает `verdict` и `violations`. При техническом сбое она сообщает об ошибке исключением; сервер переводит задание в `failed`. Нельзя заменять сбой пустым списком нарушений.

Первый реализованный профиль проверяет только наличие банкнот на столе после исчезновения человека из наблюдаемой рабочей зоны. `violation` означает признаки **возможного** нарушения с оговорками внутри `description`; это не установленное нарушение закона. `no_violation` относится только к реализованному типу и выбранным кадрам. Если положительного сигнала нет, но данные недостаточны для завершения этой проверки, анализатор вызывает `IncompleteAnalysisError`; сервер переводит задание в `failed`, не подставляя нормальный результат. До расширения профиля интерфейс должен понятно показывать его ограниченный объём. Схема ответа остаётся прежней.

В первом правиле `timecode_sec` — исходное время второго последовательного модельного совпадения условий, то есть момент срабатывания правила. Это не точная секунда ухода. В `description` остаются первый признак, момент подтверждения и ограничения; соответствующий кадр входит в `evidence_frames`. Подробности: [RULES.md](RULES.md).

Модель загружается один раз на исполнителя и повторно используется. Данияр предоставляет инструкции загрузки весов, запуска и проверки готовности. Сервер использует одного исполнителя анализа на GPU на старте; увеличение параллельности требует замеров.

## Публичный API жюри: сторона Касымбека

Оба маршрута проверяют заголовок `X-API-Key`. Неверный или отсутствующий ключ отклоняется до запуска анализа. Настоящий ключ хранится на сервере вне Git и не попадает в браузерную сборку.

### Загрузка

`POST /api/v1/analyze`

Тело: `multipart/form-data`, файл `.mov` в поле `file`.

Сервер сохраняет файл в отдельное место для задания, регистрирует его и возвращает JSON с `job_id`, не ожидая завершения анализа. Имена загружаемых файлов нельзя использовать как общие пути хранения для всех заданий.

### Состояние и результат

`GET /api/v1/jobs/{job_id}`

Статусы только `processing`, `done`, `failed`. До завершения задания наружу возвращается `processing`, в том числе при внутреннем ожидании очереди. Не вводим публичный статус `queued` без согласования с организаторами. При неизвестном идентификаторе сервер возвращает понятную HTTP-ошибку, а не чужое задание или нормальный результат.

До окончания анализа:

```json
{"job_id": "example-job", "status": "processing"}
```

Успешно обработано, нарушений нет:

```json
{
  "job_id": "example-job",
  "status": "done",
  "verdict": "no_violation",
  "violations": []
}
```

При обнаруженных событиях `verdict` равен `violation`, а `violations` содержит один или несколько элементов:

| Поле события | Тип и смысл |
| --- | --- |
| `type` | Строка с названием типа события |
| `timecode_sec` | Число секунд от начала видео, допускается дробная часть |
| `description` | Что наблюдается, почему требуется проверка и краткая нормативная ссылка |
| `evidence_frames` | Массив из 1–3 реальных кадров данного видео |

| Поле кадра | Тип и смысл |
| --- | --- |
| `timestamp_sec` | Число секунд от начала исходного видео |
| `image_base64` | JPEG в base64 без префикса `data:image/jpeg;base64,` |

Префикс добавляет интерфейс для отображения. В тестовом режиме допустимы явно обозначенные синтетические изображения. В рабочем режиме доказательства извлекаются только из входного видео.

Сервер проверяет структуру результата анализатора перед `done`: допустимый вердикт, соответствие пустого/непустого списка, числовые таймкоды, обязательные поля и 1–3 кадра. Невалидный результат означает `failed`; сервер не должен самостоятельно придумывать события или исправлять смысл анализа.

При сбое:

```json
{"job_id": "example-job", "status": "failed"}
```

У `failed` нет вердикта `no_violation`. Подробную техническую причину можно записывать в локальный журнал без секретов; интерфейс должен уметь показать ошибку даже без дополнительного поля с её описанием.

Отдельное поле нормативного источника не добавляем в обязательный ответ жюри без согласования. Пока показываем источник внутри `description`; интерфейс его не обрезает. Закрытый список типов событий на frontend не фиксируем.

## Браузер и сервер

Касымбек делает frontend и сервер, поэтому сам согласованно реализует их внутреннее соединение. Браузер может использовать отдельные маршруты того же приложения, вызывающие общую службу заданий на сервере. Они не обязаны делать HTTP-запрос к собственному публичному API. Общий секрет жюри браузеру не передаётся.

Опрос состояния можно выполнять раз в две секунды. Он прекращается после `done`, `failed` или ухода с экрана. Сетевой сбой не превращается автоматически в повторную загрузку видео.

## Интеграция и время

Для первой версии сервер, исполнитель анализа и файлы запускаются на ноутбуке Данияра с RTX 5070. На ноутбуке Касымбека весь сценарий можно разрабатывать с явно включённым тестовым анализатором, возвращающим такую же структуру.

Рабочий режим не должен незаметно включать тестовые ответы при отсутствии модели или ошибке её загрузки. При перезапуске ранее незавершённые задания не должны бесконечно оставаться `processing`: их состояние нужно восстановить либо перевести в понятный сбой.

Лимит кейса — результат за пять минут; точное начало отсчёта и параллельность жюри не уточнены. Измеряем ожидание очереди, чтение видео, анализ и подготовку ответа, а загрузку файла учитываем отдельно. Два одновременно поступивших задания — наша дополнительная проверка, не заявленный организаторами профиль нагрузки. Очередь сама по себе не гарантирует соблюдение лимита.
