# Формат обмена между анализатором, сервером и интерфейсом

Этот документ фиксирует договорённость команды. Публичные маршруты и поля результата взяты из кейса ForteBank; внутренняя функция, организация очереди и маршруты браузера — наши решения реализации. Сервер находится в `backend/`; настоящий локальный путь, запуск через Funnel и внешняя загрузка через сайт подтверждены для текущего профиля с одним правилом. Маршруты, версии, измерения и ограничения проверок указаны в [протоколе интеграции](FUNNEL_INTEGRATION_STATUS.md) и [статусе этапов 4–5](STAGE45_STATUS.md). Изменения общей схемы согласуются обеими сторонами до реализации.

## Внутренний анализатор: сторона Данияра

Python-модуль: `analyzer/service.py`. Точка входа сохраняет вызов `analyze_video(video_path: str) -> dict`; полная сигнатура — `analyze_video(video_path: str, *, budget_sec: float = 260.0) -> dict`.

`budget_sec` — необязательный для прямого вызова внутренний аргумент. Сервер передаёт оставшееся после загрузки, проверки видео и очереди время с запасом на возврат ответа, не более 260 секунд. В публичный запрос этот параметр не добавляется. Истечение бюджета не должно превращаться в успешный отрицательный результат.

Сервер требует явно объявленный параметр `budget_sec`, принимающий именованный аргумент. Анализатор с поддержкой только одного аргумента отклоняется без перехода в mock.

Модуль также предоставляет `check_ready()` без аргументов: он проверяет готовность и идентичность нужных локальных моделей. Текущая реализация возвращает сведения об обеих моделях. Исключение или явный `False` означают неготовность. Исполнитель допускает `None`, но предварительная диагностика Funnel строже: требует список или кортеж из двух записей и доступность обоих модельных `/health`. Сервер проверяет готовность при старте, перед каждым анализом и периодически во время простоя. Это не проверка качества распознавания.

Сервер передаёт абсолютный путь к уже сохранённому видео на компьютере, где работает анализатор. Анализатор не принимает HTTP-запросы, не создаёт `job_id` и не управляет API-ключами. Вызов блокирует своего исполнителя до получения результата; сервер обязан запускать его вне обработки HTTP-запроса.

При успешной обработке функция возвращает `verdict` и `violations`. При техническом сбое она сообщает об ошибке исключением; сервер переводит задание в `failed`. Нельзя заменять сбой пустым списком нарушений.

Первый реализованный профиль проверяет только наличие банкнот на столе после исчезновения человека из наблюдаемой рабочей зоны. `violation` означает признаки **возможного** нарушения с оговорками внутри `description`; это не установленное нарушение закона. `no_violation` относится только к реализованному типу и выбранным кадрам. Если положительного сигнала нет, но данные недостаточны для завершения этой проверки, анализатор вызывает `IncompleteAnalysisError`; сервер переводит задание в `failed`, не подставляя нормальный результат. До расширения профиля интерфейс должен понятно показывать его ограниченный объём. Схема ответа остаётся прежней.

В первом правиле `timecode_sec` — исходное время первого совпадения условий, которое затем подтверждено вторым последовательным кадром. В локальном отчёте `confirmed_at_sec` отдельно хранит момент подтверждения. Это не точная секунда ухода. В `description` указаны оба момента, границы наблюдаемого изменения и ограничения; первый совпавший кадр входит в `evidence_frames`. Несколько подтверждённых фрагментов с одной историей присутствия объединяются в один сигнал; разрывы между ними не объявляются непрерывным событием. Публичные поля не изменены. Подробности: [RULES.md](RULES.md).

Веса загружаются в два локальных сервера моделей (2B на `127.0.0.1:8080`, 4B на `127.0.0.1:8081`) и повторно используются между заданиями. `check_ready()` проверяет объявленные имена весов обеих ролей при запуске исполнителя и перед анализом. Данияр предоставляет инструкции загрузки весов, запуска и проверки готовности. Сервер использует одного исполнителя анализа на GPU; увеличение параллельности требует замеров.

## Публичный API жюри: сторона Касымбека

Оба маршрута проверяют заголовок `X-API-Key`. Неверный или отсутствующий ключ отклоняется до запуска анализа. Настоящий ключ хранится на сервере вне Git и не попадает в браузерную сборку.

### Загрузка

`POST /api/v1/analyze`

Тело: `multipart/form-data`, файл `.mov` в поле `file`.

Сервер сохраняет файл в отдельное место для задания, регистрирует его и возвращает JSON с `job_id`, не ожидая завершения анализа. Имена загружаемых файлов нельзя использовать как общие пути хранения для всех заданий.

### Состояние и результат

`GET /api/v1/jobs/{job_id}`

Статусы только `processing`, `done`, `failed`. До завершения задания наружу возвращается `processing`, в том числе при внутреннем ожидании очереди. Не вводим публичный статус `queued` без согласования с организаторами. При неизвестном идентификаторе сервер возвращает понятную HTTP-ошибку, а не чужое задание или нормальный результат.

До окончания анализа:

```json
{"job_id": "example-job", "status": "processing"}
```

Успешно обработано, нарушений нет:

```json
{
  "job_id": "example-job",
  "status": "done",
  "verdict": "no_violation",
  "violations": []
}
```

При обнаруженных событиях `verdict` равен `violation`, а `violations` содержит один или несколько элементов:

| Поле события | Тип и смысл |
| --- | --- |
| `type` | Строка с названием типа события |
| `timecode_sec` | Число секунд от начала видео, допускается дробная часть |
| `description` | Что наблюдается, почему требуется проверка и краткая нормативная ссылка |
| `evidence_frames` | Массив из 1–3 реальных кадров данного видео |

| Поле кадра | Тип и смысл |
| --- | --- |
| `timestamp_sec` | Число секунд от начала исходного видео |
| `image_base64` | JPEG в base64 без префикса `data:image/jpeg;base64,` |

Префикс добавляет интерфейс для отображения. В тестовом режиме допустимы явно обозначенные синтетические изображения. В рабочем режиме доказательства извлекаются только из входного видео.

Сервер проверяет структуру результата анализатора перед `done`: допустимый вердикт, соответствие пустого/непустого списка, числовые таймкоды, обязательные поля и 1–3 кадра. Невалидный результат означает `failed`; сервер не должен самостоятельно придумывать события или исправлять смысл анализа.

При сбое:

```json
{"job_id": "example-job", "status": "failed"}
```

У `failed` нет вердикта `no_violation`. Подробную техническую причину можно записывать в локальный журнал без секретов; интерфейс должен уметь показать ошибку даже без дополнительного поля с её описанием.

Отдельное поле нормативного источника не добавляем в обязательный ответ жюри без согласования. Пока показываем источник внутри `description`; интерфейс его не обрезает. Закрытый список типов событий на frontend не фиксируем.

## Браузер и сервер

Касымбек делает frontend и сервер, поэтому сам согласованно реализует их внутреннее соединение. Браузер может использовать отдельные маршруты того же приложения, вызывающие общую службу заданий на сервере. Они не обязаны делать HTTP-запрос к собственному публичному API. Общий секрет жюри браузеру не передаётся.

Опрос состояния можно выполнять раз в две секунды. Он прекращается после `done`, `failed` или ухода с экрана. Сетевой сбой не превращается автоматически в повторную загрузку видео.

`GET /ui/session` дополнительно возвращает `analysis_scope`: список включённых `rules`, текст `notice` и флаг `complete_case_coverage`. Эти данные получает исполнитель от `analyzer.service.describe_scope()` и передаёт интерфейсу. Текущий флаг равен `false`; интерфейс должен показывать ограниченный набор проверок. Для тестового режима или недоступного исполнителя поле может быть `null`. Это внутренний браузерный маршрут: обязательный ответ жюри сохраняет прежнюю схему.

В ответе внутреннего `/ui/jobs/{job_id}` при `failed` допускается `error_code` из закрытого безопасного списка. Интерфейс переводит его в понятное сообщение; неизвестный код означает общий технический сбой. Публичный JSON жюри этим полем не расширяется. Исторический mock-результат не переименовывается в real при смене текущего режима сервера.

Код `incomplete_analysis` означает завершённую проверку без достаточных визуальных данных. Интерфейс не называет его отсутствием нарушений и не требует перезапуска моделей. Другие безопасные коды отличают технический сбой, недоступность модели и истечение срока.

## Интеграция и время

Для первой версии сервер, исполнитель анализа и файлы запускаются на ноутбуке Данияра с RTX 5070. На ноутбуке Касымбека весь сценарий можно разрабатывать с явно включённым тестовым анализатором, возвращающим такую же структуру.

Рабочий режим не должен незаметно включать тестовые ответы при отсутствии модели или ошибке её загрузки. При перезапуске ранее незавершённые задания не должны бесконечно оставаться `processing`: их состояние нужно восстановить либо перевести в понятный сбой.

Лимит кейса — результат за пять минут; точное начало отсчёта и параллельность жюри не уточнены. Для нашей приёмки считаем весь путь от начала клиентской отправки до получения и проверки полного ответа: соединение, загрузку, ожидание очереди, чтение видео, анализ и передачу результата. Внутренний срок 285 секунд начинается при входе запроса в сервер; это не заменяет клиентский замер 300 секунд. Анализатор получает `min(260, оставшееся время - 5)` секунд; при остатке не более 15 секунд новый анализ не начинается.

Принимаются максимум два незавершённых запроса с учётом загрузок; анализ один за раз, третий запрос получает 429. Ожидание второго входит в его срок. Два одновременно поступивших задания — наша дополнительная проверка, не заявленный организаторами профиль нагрузки. Очередь сама по себе не гарантирует соблюдение лимита. После аварии/таймаута real новые задания не запускаются до проверки моделей и перезапуска приложения. Команды и границы проверки: [REAL_FUNNEL_HANDOFF.md](REAL_FUNNEL_HANDOFF.md).

Завершённый анализ без достаточного визуального подтверждения может выбросить `IncompleteAnalysisError` с `inference_completed=True`. Только это проверенное исключение разрешает исполнителю продолжить очередь; текущее задание всё равно получает `failed` без вердикта. При незавершённом проходе, техническом сбое или истечении бюджета признак остаётся `False`, новые вызовы блокируются. Публичная схема от этого не меняется.
