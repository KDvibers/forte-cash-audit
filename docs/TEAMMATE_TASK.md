# Задача Касымбеку: весь интерфейс и сервер приложения

Это обновлённое распределение для `KDvibers/forte-cash-audit`. В этом документе «ты» означает Касымбека с RTX 4050; Данияр работает на RTX 5070. Эта задача заменяет прежние варианты, в которых экран результатов отдавался Данияру или Касымбек делал только frontend.

## Граница ответственности

Данияр делает `analyzer/`: локальную модель, извлечение кадров, понимание событий, правила, нормативные источники, кадры-доказательства и проверку качества.

Ты делаешь `frontend/` и `backend/`: весь сайт, приём видео, сохранение файлов, задания, статусы, API-ключ, публичный API и отображение результата. Экран результатов полностью твой.

Вместе соединяем части и запускаем весь сервис на ноутбуке Данияра с RTX 5070. Написать сервер на своём компьютере не означает, что он обязан там остаться при финальном запуске.

## Как начать, не ожидая модели

Сначала прочитай общий [API_CONTRACT.md](API_CONTRACT.md). Это единый формат данных для обеих сторон; названия и типы полей нельзя менять по отдельности.

Для первой версии сервер делай на Python, чтобы напрямую вызывать наш Python-анализатор. Выбор frontend-стека оставляем тебе; сообщи команде, что выбрано, и зафиксируй зависимости и команду запуска. Не нужно привязываться к файлу `results.js`: расположение файлов определяется выбранным стеком.

Начни с тестового анализатора внутри своей части проекта. Подготовь четыре сценария: нормальное видео, одно событие, несколько событий и ошибка. Режим должен быть явно помечен. Не клади тестовую реализацию в `analyzer/` и не заменяй ею будущую настоящую функцию.

Тебе сейчас не нужно устанавливать модель, CUDA или организовывать обучение. Не жди настоящего ответа модели для разработки экрана результата.

## Сервер

1. Реализуй `POST /api/v1/analyze`: приём `.mov` через `multipart/form-data`, поле `file`, сохранение файла и ответ с `job_id`. Поддержи файлы около 29 МБ, как в кейсе, с запасом; не принимай 29 МБ за строгую верхнюю границу организаторов.
2. Реализуй `GET /api/v1/jobs/{job_id}` со статусами `processing`, `done`, `failed` и согласованным результатом.
3. Проверяй `X-API-Key` на обоих публичных маршрутах. Настоящий ключ держи только на сервере, вне репозитория. Для браузера сделай отдельное внутреннее соединение с общей службой заданий, чтобы не встраивать секрет в JavaScript.
4. Запускай анализ в фоне: HTTP-запрос загрузки не должен ждать модель, а запросы статуса должны отвечать во время обработки. Начни с очереди и одного исполнителя анализа на GPU.
5. Предусмотри адаптер, который вызывает `analyzer.service.analyze_video(video_path)` и получает словарь с `verdict` и `violations`. Сервер добавляет `job_id` и `status`. Подключение настоящего анализатора не должно требовать переделки маршрутов и экранов.
6. Передавай абсолютный путь к существующему файлу на том же компьютере. Не удаляй файл до завершения анализа. Если интерфейс использует серверную копию видео, сохраняй её до окончания просмотра по согласованному сроку очистки.
7. Ошибка анализатора, повреждённое видео или невалидный результат означают `failed`. Их нельзя превращать в «нарушений нет». Обработай неизвестный номер задания и ошибки сети понятным образом.
8. Не запускай несколько экземпляров большой модели на каждый HTTP-запрос. Количество исполнителей, загрузку модели и повторное использование согласуем при интеграции. Таймаут HTTP-запроса сам по себе не останавливает выполняющуюся GPU-задачу.

## Весь интерфейс, включая результат

На одном понятном экране пользователь:

1. Выбирает или перетаскивает `.mov`, видит название и размер.
2. Нажимает «Проверить видео».
3. Видит этап загрузки, затем «Видео обрабатывается». Не показывай выдуманный процент анализа.
4. Получает «Нарушение не обнаружено» либо «Обнаружены признаки возможных нарушений».
5. Для каждого события видит тип, время `мм:сс`, полное объяснение с источником и 1–3 кадра. Кадры можно увеличить, их собственные времена тоже видны.
6. При ошибке понимает, что обработка не завершилась, и может повторить попытку.

Не запускай случайные дубликаты задания при повторном нажатии. Прекращай опрос после завершения и при уходе с экрана. Несколько событий должны отображаться отдельными карточками.

Переход видеоплеера к событию по нажатию на таймкод — следующий приоритет после основного сценария. Регистрация, история, экспорт и пакетная загрузка сейчас не нужны.

## Проверка готовности

Сначала покажи полный путь на явно обозначенных тестовых данных: загрузка через сайт → реальный серверный `job_id` → ожидание → результат. Это первая контрольная точка, а не финальное решение кейса.

После подключения нашего анализатора повторяем тот же путь с настоящим видео на RTX 5070. Отдельно проверяем прямые запросы к API без интерфейса, неверный ключ, сбой анализа, несколько событий, самый длинный ролик, перезапуск и два поступивших задания. Для каждого задания измеряем полное время, а не только среднее по двум запускам. Новые сложные функции добавляем после работающего основного пути.

В рабочем режиме тестовые ответы отключены. При неготовой модели сервер сообщает о проблеме, а не показывает выдуманный успешный результат.

## Файлы и совместная работа

Твоя локальная ветка: `web-api`. Данияр работает над анализатором в ветке `analyzer`.

Меняй `frontend/` и `backend/`; не меняй `analyzer/` без согласования. Держи зависимости своей части внутри её папок. Изменения общих файлов, способа запуска, правил совместной работы и API-контракта сначала согласуй с командой, чтобы не получить несовместимые версии.

Push и создание PR выполняет только Данияр. Подготовь локальные изменения и передай Данияру патч либо архив только своих исходников для просмотра и публикации. Не передавай `.git`, зависимости, секреты или данные вместе с таким архивом. Сохраняем настоящее авторство каждого участника.

Не добавляй в Git исходные видео, таблицу разметки, извлечённые кадры, веса моделей, ключи и пользовательские загрузки. Для тестовых картинок используй нейтральные заглушки. Все производственные AI-вызовы остаются внутри нашего сервиса; облачные AI API, анализ аудио и идентификация лиц запрещены кейсом.

Результат твоей работы: работающие frontend и backend, тестовый режим для разработки, адаптер к анализатору, список зависимостей и короткая инструкция запуска. Данияр отвечает за настоящие выводы анализатора; ты отображаешь их без придумывания или изменения смысла.
